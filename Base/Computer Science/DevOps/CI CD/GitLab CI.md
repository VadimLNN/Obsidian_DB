# GitLab CI

[Навигация](README.md) · Источник: [оригинал](../CI%20CD%20курс%20ориг.md), разделы «Что такое pipeline, jobs и stages», «Первый .gitlab-ci.yml», примеры с [[Docker]] и деплоем. Устройство executors и современные правила запуска раскрыты дополнительно.

## Платформа, runner и executor

**GitLab** хранит код и конфигурацию, обрабатывает события, создаёт pipeline, планирует jobs и показывает результаты. **GitLab Runner** — отдельная программа, выполняющая назначенные jobs. Она может работать на другом сервере, чем сам GitLab.

Runner аутентифицируется в GitLab и запрашивает подходящие задания по API; для ожидания может использоваться long polling. Планировщик учитывает доступность runner для проекта, tags, ограничения protected refs и свободные ресурсы. Получив job, runner готовит среду, получает исходники нужного commit, восстанавливает нужные данные, выполняет команды и отправляет логи, статус и артефакты обратно.

**Job — описание конкретной работы, runner — исполнитель многих jobs, executor — способ запуска этой работы.** Установка runner на машину не означает, что каждая job получает виртуальную машину.

| Executor | Где выполняется `script` | Что учитывать |
|---|---|---|
| Shell | В shell на машине runner от его пользователя | Инструменты устанавливает администратор; `image` не создаёт контейнер; остаются файлы и доступ к хосту |
| Docker | В контейнере из `image`; рядом возможны `services` | Отдельная файловая система контейнера, но общее ядро и явно подключённые volumes |
| [[Kubernetes]] | В контейнерах [[Pod]], создаваемого для job | Нужны кластер и права runner; расписание и лимиты Pod влияют на запуск |

Это основные варианты для понимания; полный список шире. [Runner executors](https://docs.gitlab.com/runner/executors/) и [выполнение Docker executor](https://docs.gitlab.com/runner/executors/docker/) описывают различия и фазы подготовки.

Порядок для обычной контейнерной job:

```text
GitLab: событие → проверка YAML/правил → pipeline → очередь jobs
                                                     │
Runner: запрос задания → подготовка executor → checkout commit
                                                     │
                restore cache → download artifacts → before_script
                                                     │
                     script → after_script → upload artifacts/cache
                                                     │
                                  отчёт статуса и очистка среды
```

При отсутствии подходящего runner job остаётся `pending`/stuck; это ещё не падение тестов. Если runner пропал уже во время выполнения, job может завершиться ошибкой инфраструктуры или таймаутом. Проверяй online/paused, tags, доступ к проекту, protected-настройки, лимиты параллельности и сеть.

Git tags (`v1.0.0`) и runner tags (`docker`, `linux`) — разные сущности: первые обозначают Git refs, вторые выбирают исполнителей. Runner должен соответствовать всем tags job. Jobs без tags требуют runner, допускающего untagged jobs.

## YAML как конфигурация

`.gitlab-ci.yml` обычно лежит в корне репозитория. GitLab разбирает структуру [[YAML]], а shell исполняет строки `script`. Валидный YAML может содержать неверные для GitLab ключи или команды для отсутствующего инструмента.

| Конструкция | Назначение |
|---|---|
| `default: image:` | Образ по умолчанию для поддерживающих его executors |
| `stages` / `stage` | Порядок этапов / этап конкретной job |
| `before_script` / `script` / `after_script` | Подготовка / команды / завершающие действия |
| `variables` | Несекретные настройки; значения в окружении процесса являются строками |
| `workflow: rules` | Создавать ли pipeline по данному событию |
| `rules` внутри job | Добавлять ли job и с какими параметрами |
| `needs` | Явные зависимости между jobs |
| `artifacts` | Сохранение результатов и передача в следующие jobs |
| `cache` | Необязательные повторно используемые данные для ускорения |
| `environment` | Метаданные целевого окружения, а не команда создания сервера |
| `when: manual` | Запуск job после ручного действия |

Это обычная схема job с `script`. Утверждение курса «script всегда обязателен» слишком широкое: например, существуют trigger jobs для downstream pipelines. Полный синтаксис — в [GitLab YAML reference](https://docs.gitlab.com/ci/yaml/).

Отступы — пробелами, уровень вложенности должен быть согласован. Для строк с `: ` удобно использовать YAML block scalar:

```yaml
show_version:
  script:
    - |
      printf 'Commit: %s\n' "$CI_COMMIT_SHA"
```

Это самостоятельная демонстрационная job: в стандартном push pipeline выводит SHA, ничего не собирает. Кавычки shell внутри незаключённого в YAML-кавычки значения не всегда спасают от интерпретации двоеточия YAML-парсером. Не копируй псевдокод `job: run_tests` из оригинала в рабочую конфигурацию: настоящая job задаётся собственным ключом `run_tests:`.

`before_script` и `script` выполняются в контексте основного shell job. `after_script` запускается отдельно: нельзя полагаться на сделанный внутри `script` `export` как на способ передачи состояния в него. Между jobs переменные shell также не переходят автоматически.

## Рабочий CI для учебного приложения

Полный файл: [.gitlab-ci.yml](examples/ci-demo/.gitlab-ci.yml). Само приложение и запуск — в [практике](Практика.md). Здесь тот же файл приведён для разбора:

```yaml
default:
  image: node:22-bookworm-slim

workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS && $CI_PIPELINE_SOURCE == "push"'
      when: never
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH'
    - when: never

stages: [test, build]

syntax:
  stage: test
  script:
    - npm run check

test:
  stage: test
  variables:
    APP_ENV: test
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - .npm/
  script:
    - npm ci --cache .npm --prefer-offline --no-audit --no-fund
    - npm test

build:
  stage: build
  script:
    - npm ci --no-audit --no-fund
    - npm run build
    - node --check dist/app.cjs
    - tar -czf app.tar.gz -C dist app.cjs
  artifacts:
    name: 'app-$CI_COMMIT_SHA'
    paths:
      - dist/
      - app.tar.gz
    expire_in: 7 days
```

**Предпосылки:** файлы `examples/ci-demo/` скопированы в корень отдельного GitLab-репозитория, есть доступный Docker executor с поддержкой untagged jobs и доступом к образу Node. Если runner требует tags, добавь подходящие tags в `default`. Команды рассчитаны на Linux.

**События и результат:**

| Событие | Создаётся pipeline? | Какие jobs |
|---|---|---|
| Push ветки без открытого MR | Да | `syntax`, `test`, затем `build` |
| MR или обновление source-ветки открытого MR | Да, MR pipeline | Те же проверки и сборка |
| Push source-ветки с открытым MR | Отдельный push pipeline запрещён | Избегаем второго запуска для того же изменения |
| Push тега | Нет | Правило требует `CI_COMMIT_BRANCH` |
| Schedule, API, Run pipeline в UI | Нет | Их не разрешает `workflow` |

Правила проверяются сверху вниз до первого совпадения. Создание MR pipelines нужно разрешить отдельно — наличие YAML само по себе не включает все виды событий. `workflow` оценивается до job rules. [Правила pipeline](https://docs.gitlab.com/ci/yaml/workflow/) и [правила jobs](https://docs.gitlab.com/ci/jobs/job_rules/) описывают этот порядок и проблему дублирующих запусков.

`syntax` и `test` могут идти параллельно. Первая проверяет синтаксис Node, **не заменяя полноценный линтер**. Вторая реально выполняет HTTP-проверки приложения. `build` ждёт обеих jobs, создаёт `dist/app.cjs` и `app.tar.gz`, затем runner загружает их в GitLab. Деплоя в этой конфигурации нет.

В примере нет сторонних npm-зависимостей, поэтому кэш почти не даёт выигрыша. Он оставлен как небольшая демонстрация механизма курса; при добавлении зависимостей начнёт сокращать загрузки. Флаги `--no-audit --no-fund` убирают дополнительные сетевые обращения/сообщения при установке, **не выполняют security-проверку**. Её нужно проектировать отдельно.

## Артефакт и кэш — разные договорённости

| Свойство | Artifact | Cache |
|---|---|---|
| Зачем | Сохранить результат конкретной job, передать дальше | Избежать повторной загрузки/вычисления |
| Примеры | `dist/`, архив, отчёт тестов | `.npm/`, скачанные пакеты |
| Привязка | Job и pipeline; имя может включать commit | Ключ; возможно повторное использование между запусками |
| Если отсутствует | Нужный deploy/test должен остановиться | Job должна восстановить данные и продолжить |
| Где хранится | Хранилище artifacts GitLab | Локально у runner или в настроенном распределённом cache |
| Можно ли хранить секреты | Нет | Нет |

Артефакт создаётся в рабочей директории, загружается после job, скачивается потребителем, затем удаляется согласно политике хранения. `expire_in` задаёт срок, но сохранение последних успешных artifacts и ручное Keep могут влиять на фактическое удаление. Выбирай срок, покрывающий ожидание ручного релиза. Docker-образы живут в registry по отдельной политике, их не сохраняет `artifacts: paths`. [Жизненный цикл artifacts](https://docs.gitlab.com/ci/jobs/job_artifacts/).

По умолчанию последующие stages могут скачивать artifacts предыдущих stages. Явные `needs` ограничивают их источники. Например, **добавь** к учебному YAML следующий stage `verify` после `build` и эту job:

```yaml
verify_package:
  stage: verify
  needs:
    - job: build
      artifacts: true
  script:
    - tar -tzf app.tar.gz
    - node --check dist/app.cjs
```

События наследуются от `workflow`. После `build` job получит архив и каталог, выведет `app.cjs` из архива и проверит синтаксис доставленного файла. Если забыть добавить `verify` в `stages`, конфигурация будет некорректной. Если не сохранить или не скачать файл, команды завершатся ошибкой.

`needs` — не просто ускоритель: он меняет граф. Deploy с зависимостью только от build способен обойти другие проверки, если build их не ждёт. Просматривай весь путь до production. Не смешивай `needs` и `dependencies` в одной job без понимания ограничений платформы.

Кэш не гарантирован: другой runner может его не иметь. Ключ по lock-файлу отделяет наборы зависимостей; при зависимости от ОС/архитектуры/версии runtime включают и эти параметры. Несколько jobs с одним ключом могут перезаписывать кэш. Нельзя делать deploy из кэша или смешивать кэш доверенных и недоверенных сборок. [GitLab caching](https://docs.gitlab.com/ci/caching/).

### Почему npm ci, а не npm install

`npm install` нужен при изменении зависимостей разработчиком. В CI `npm ci` требует lock-файл, проверяет согласованность с `package.json`, очищает существующий `node_modules` и устанавливает фиксированное дерево. Поэтому кэш скачанных пакетов `.npm/` полезнее наивного кэша `node_modules/`, который `npm ci` всё равно удалит. Lifecycle scripts зависимостей могут выполнять код — lock-файл не делает их автоматически безопасными. [Документация npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/).

## Manual jobs и правила релиза

В курсе встречается `only: [main]`. Для чтения старых файлов его нужно знать, но новые примеры используют `rules`: `only/except` помечены deprecated. Не задавай `only` и `rules` вместе в одной job. [Устаревшие ключи GitLab](https://docs.gitlab.com/ci/yaml/deprecated_keywords/).

Фрагмент **существующей production-job**, не самостоятельный pipeline:

```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    when: manual
allow_failure: false
```

Так job существует только для push основной ветки, требует ручного запуска и не считается необязательной. У `when: manual` вне `rules` и внутри `rules` различаются значения `allow_failure` по умолчанию, поэтому здесь значение явно задано. Ручная кнопка не заменяет права, защищённую ветку и ограничение доступа к секретам. Полная последовательность staging → production — в [деплое](Деплой%20и%20безопасность.md).

## Расширенные возможности из обзора курса

- **Matrix:** комбинации параметров, например Node × ОС; в настоящем GitLab используется `parallel:matrix`, а не псевдоключ `matrix` из рисунка курса. Каждая комбинация расходует ресурсы.
- **Child pipeline:** дочерний pipeline для частей одного проекта. Динамическая генерация конфигурации полезна для больших репозиториев, но осложняет диагностику.
- **Multi-project pipeline:** запуск процесса в другом проекте через trigger с проверкой прав и передачи параметров.
- **Review Apps:** временная среда для ветки/MR. Нужны создание, уникальное имя, маршрутизация и удаление, а не только `environment`.
- **Выборочные проверки:** `rules:changes` помогает пропускать нерелевантные jobs; ошибочные зависимости путей могут пропустить нужный тест.
- **Security scanners и отчёты:** возможности зависят от версии, конфигурации и редакции GitLab. Одно упоминание сканера в YAML не доказывает защиту.

Курс даёт обзор этих механизмов, а не готовую инфраструктуру. Сначала добейся воспроизводимого простого CI.

## Диагностика и что важно запомнить

Сначала различи четыре случая: pipeline не создан; job ожидает runner; runner не смог подготовить среду; команда приложения завершилась ошибкой. Это разные уровни, и повтор `npm test` не исправит несовпадение tags.

Проверяй файл через **CI Lint / Pipeline editor** в своём GitLab, включая доступные там проверки логики создания pipeline. Локальный YAML-парсер обнаружит формат, но не проверит права, версии GitLab и доступность runners. Далее смотри первый ошибочный шаг и commit, для которого он запущен.

Главное: GitLab планирует, runner исполняет, executor определяет среду; `rules` управляет составом, `needs` — зависимостями, artifacts — результатами, cache — скоростью.

## Проверка понимания

**Runner недоступен: значит тесты упали?** Нет. Job ещё могла не начать исполняться; смотри очередь и подбор runner.

**Почему `image: node:22-bookworm-slim` не помогает Shell executor?** Shell запускает команды на хосте. Нужен Node на хосте либо другой executor.

**Почему build не видит файлы test-job?** Рабочие директории jobs не являются контрактом обмена. Передай нужный результат как artifact или повтори подготовку среды.

**Почему кэш нельзя использовать вместо артефакта?** Он может отсутствовать, быть перезаписан и не соответствовать нужному запуску. Результат релиза должен иметь явное происхождение.

**Что будет после удаления кэша?** Корректная job заново скачает зависимости; изменится скорость, а не смысл результата.

**Почему после `needs: [build]` можно случайно пропустить тест?** Job ждёт только заявленные зависимости; если build не зависит от этого теста, связи с ним нет.
