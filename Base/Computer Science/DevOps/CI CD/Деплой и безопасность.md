# Деплой, конфигурация и безопасность

[Навигация](README.md) · Источник: [оригинал](../CI%20CD%20курс%20ориг.md), разделы Continuous Delivery, Continuous Deployment, «Что такое деплой и переменные окружения». Готовая реализация через Compose и защита [[SSH и передача файлов|SSH]] — дополнительные материалы.

## Что считается деплоем

Deploy — развёртывание выбранной версии приложения в целевом окружении. Оно включает получение артефакта, применение конфигурации, при необходимости совместимые миграции данных, запуск/обновление процесса и проверку результата.

`echo 'Деплой завершён'` в оригинальном примере только выводит строку. Даже успешный `scp` подтверждает лишь передачу файлов. Успех `kubectl apply` означает принятие желаемой конфигурации API, но не готовность всех Pod и бизнес-функций.

Нужно уметь ответить: какой commit и artifact развёрнуты, где, кем разрешён выпуск, какие проверки пройдены и как восстановить предыдущую рабочую версию.

## Окружения и build once, deploy many

| Окружение | Назначение | Данные и доступ |
|---|---|---|
| Development | Локальная разработка или общий dev-стенд | Тестовые данные, минимум привилегий |
| Testing / CI | Автоматические проверки конкретного запуска | Одноразовые fixtures и изолированные сервисы |
| Staging | Проверка кандидата в условиях, близких к production | Обезличенные/синтетические данные, отдельные credentials |
| Production | Работа для реальных пользователей | Контролируемые права, мониторинг, резервное копирование |

В разных разделах курса development означает то локальный компьютер, то общий стенд: это два употребления термина, а не обязательная топология. Названия окружений — договорённость команды. Staging должен быть похож на production по существенным свойствам, но равенство железа и объёма данных не всегда возможно.

**Build once, deploy many**: собираем артефакт один раз, проверяем его на staging и продвигаем тот же результат в production. Настройки среды подаются при запуске. Если приложение встраивает URL в frontend bundle при сборке, одной замены runtime-переменной недостаточно: нужна поддержка runtime-конфигурации либо честное признание отдельных сборок.

Схема курса `develop → build → staging` и `main → build → production` полезна для объяснения правил веток, но две сборки не гарантируют один и тот же artifact. Для продвижения конкретного релиза нужно повторно использовать сохранённый artifact/digest. В примере ниже staging и production используют образ одного pipeline основной ветки.

## Переменные окружения и .env

Переменная окружения — строковое значение, доступное процессу и обычно наследуемое дочерними процессами. Приложение должно явно читать и интерпретировать его; `DEBUG=false` — строка, которая в JavaScript сама по себе truthy.

```javascript
const debug = process.env.DEBUG === 'true';
const environment = process.env.APP_ENV || 'development';
```

```python
import os

debug = os.environ.get('DEBUG') == 'true'
database_url = os.environ['DATABASE_URL']
```

Во втором примере отсутствие обязательного `DATABASE_URL` приводит к ошибке старта, а не к случайному подключению к неподходящей БД. Для обязательных production-настроек это полезнее скрытых значений по умолчанию. Секрет не нужно печатать в сообщении об ошибке.

В учебном приложении `APP_ENV` обозначает среду; не используется нестандартный `NODE_ENV=staging`. Библиотеки Node часто рассчитывают на `development`, `test`, `production`, а `NODE_ENV=production` влияет в том числе на установку devDependencies.

`.env` — обычный файл, не механизм шифрования. Shell и произвольное приложение не обязаны автоматически его читать: нужен loader или поддержка инструмента. В [[Docker|Docker Compose]] `.env` может использоваться для подстановки в YAML; переменная попадёт в контейнер через `environment`/`env_file`, а не просто из-за наличия файла.

В Git сохраняют `.env.example` с названиями и безопасными заглушками. Настоящий `.env` добавляют в `.gitignore`, но ignore не удаляет уже закоммиченный секрет из истории. При утечке сначала отзывают/меняют credential, затем устраняют следы и причину утечки.

## Где хранить и кому выдавать secrets

GitLab предоставляет CI/CD variables в настройках проекта/группы. Секреты задают там или в специализированном хранилище, а YAML содержит только имена. Различай свойства:

| Свойство | Что даёт | Чего не даёт |
|---|---|---|
| Masked | Сокрытие подходящих значений в логах | Защиту от намеренной отправки секрета скриптом |
| Hidden | Ограничение последующего просмотра значения в UI | Запрет доступа выполняющей job |
| Protected | Ограничение выдачи для разрешённых protected refs с учётом правил платформы | Проверку корректности самого pipeline-кода |
| Environment scope | Выдачу только jobs подходящего окружения | Автоматическое создание/защиту сервера |
| File variable | Временный файл; в переменной — путь к нему | Шифрование файла от самой job |

Доступность и конкретные условия зависят от версии/редакции. Маскирование имеет ограничения формата, поэтому многострочный SSH private key не следует слепо объявлять masked. Важнее file variable, protected scope и отсутствие вывода содержимого. [GitLab variables](https://docs.gitlab.com/ci/variables/).

Jenkins выдаёт секреты через Credentials и ограниченный блок `environment` или `withCredentials`; подробности — в [Jenkins](Jenkins.md). [Vault](../Vault.md) — направление для централизованной выдачи и ротации секретов, в курсе развёртывание Vault не изучается.

Pipeline выполняет код из репозитория и зависимостей. Поэтому проверяют не только YAML, но и вызываемые `npm` scripts, Dockerfile, shell-скрипты и внешние шаблоны. Недоверенная ветка не должна получать production-ключи. Ручное разрешение запуска не обезвреживает вредоносный код автоматически.

## Практика: доставка контейнера на два сервера

Это **дополнение**, реализующее общую схему курса. Оно расширяет [учебный GitLab CI](examples/ci-demo/.gitlab-ci.yml). Платформа остаётся GitLab CI, приложение — тот же Node.js-сервис. Compose нужен только для короткого воспроизводимого обновления контейнера.

### Предпосылки

1. В учебном проекте включён GitLab Container Registry, default branch защищена и **не используется как source-ветка открытого MR** при данных `workflow:rules`.
2. CI-тесты и build выполняет Docker executor. Публикацию — выделенный доверенный **Shell runner** с tag `docker-builder`, Docker CLI и daemon. Это учебный выбор архитектуры, не настройка через `image`.
3. Deploy выполняет отдельный доверенный Shell runner с tag `deploy-shell`, OpenSSH client и доступом к серверам. Build/deploy runners ограничены защищённой веткой и проектом.
4. Есть **два отдельных учебных Linux-сервера**: staging и production. На каждом установлены Docker и Compose v2 с поддержкой `up --wait`, свободен localhost:8080, создан отдельный deploy-пользователь и каталог `/opt/ci-demo`. Доступ пользователя к Docker имеет высокие привилегии и ограничивается этим стендом.
5. На каждом сервере администратор заранее разместил [compose.yaml](examples/ci-demo/compose.yaml) в `/opt/ci-demo/compose.yaml` и настроил чтение приватного registry отдельным read-only credential. Краткоживущий пароль CI job не сохраняют как постоянный production credential.
6. В GitLab созданы environment-scoped variables для `staging` и `production`: `DEPLOY_HOST`, `DEPLOY_USER`, file variables `SSH_PRIVATE_KEY` и `SSH_KNOWN_HOSTS`. Для каждой среды — свои значения, только защищённые refs. SSH key соответствует `authorized_keys` сервера; `known_hosts` получен администратором по доверенному каналу. Ключи остаются в UI/хранилище, не в Git.

`SSH_KNOWN_HOSTS` защищает от подключения к подменённому серверу. Не используй `StrictHostKeyChecking=no` и не получай fingerprint через непроверенный `ssh-keyscan` непосредственно во время job. [SSH в GitLab CI](https://docs.gitlab.com/ci/jobs/ssh_keys/).

Compose-конфигурация публикует сервис только на **127.0.0.1 сервера**. Для внешнего доступа нужен отдельно настроенный reverse proxy/TLS; этот пример его не создаёт.

### Расширение GitLab YAML

В исходном учебном файле **замени** `stages` на `[test, build, package, staging, production]`, остальные существующие jobs сохрани и добавь следующий блок. Это расширение, а не самостоятельная конфигурация; `build` уже определена в исходном файле.

```yaml
build_image:
  stage: package
  tags: [docker-builder]
  needs:
    - job: build
      artifacts: true
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
  script:
    - |
      export DOCKER_CONFIG
      DOCKER_CONFIG=$(mktemp -d)
      trap 'docker logout "$CI_REGISTRY" >/dev/null 2>&1' EXIT
      printf '%s' "$CI_REGISTRY_PASSWORD" | docker login "$CI_REGISTRY" \
        --username "$CI_REGISTRY_USER" --password-stdin
      image_ref="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA-$CI_PIPELINE_ID"
      docker build -t "$image_ref" .
      docker push "$image_ref"

.deploy:
  tags: [deploy-shell]
  dependencies: []
  resource_group: $CI_ENVIRONMENT_NAME
  script:
    - |
      test -s "$SSH_PRIVATE_KEY"
      test -s "$SSH_KNOWN_HOSTS"
      chmod 600 "$SSH_PRIVATE_KEY"
      image_ref="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA-$CI_PIPELINE_ID"
      ssh -i "$SSH_PRIVATE_KEY" \
        -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes \
        -o UserKnownHostsFile="$SSH_KNOWN_HOSTS" \
        "$DEPLOY_USER@$DEPLOY_HOST" \
        "APP_IMAGE='$image_ref' APP_ENV='$CI_ENVIRONMENT_NAME' docker compose \
          --project-name ci-demo -f /opt/ci-demo/compose.yaml \
          up -d --wait --wait-timeout 60"

deploy_staging:
  extends: .deploy
  stage: staging
  environment:
    name: staging
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

deploy_production:
  extends: .deploy
  stage: production
  environment:
    name: production
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push" && $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: manual
  allow_failure: false
```

**Событие:** только push default branch добавляет package/deploy jobs. Feature branch/MR проходят CI без доступа к deploy. Значения для удалённой команды формируются из GitLab registry path, SHA, числового pipeline ID и фиксированных имён environments. Не заменяй их произвольными пользовательскими параметрами без валидации и корректного shell quoting.

**Порядок:** test/syntax → build → публикация образа → staging и ожидание healthcheck → ручное подтверждение → production и healthcheck. `build` уже ждёт обязательные тесты. Production находится в отдельном stage и не обгоняет staging. При ошибке staging штатный production-путь блокируется. `allow_failure: false` делает manual job обязательной.

**Результат:** один и тот же образ с тегом `SHA-pipelineID` работает на двух серверах, но `APP_ENV` различается. `docker compose up` пересоздаёт сервис при изменении образа; `--wait` ожидает running/healthy. В `compose.yaml` healthcheck вызывает `/health`, поэтому недоступный процесс не считается успешно развёрнутым. [Поведение Compose up](https://docs.docker.com/reference/cli/docker/compose/up/).

После деплоя на каждом сервере можно проверить:

```bash
curl --fail http://127.0.0.1:8080/health
curl --fail http://127.0.0.1:8080/
```

Ожидаются `status: ok` и соответствующее `environment`. Внешний reverse proxy и пользовательские сценарии этой проверкой не покрыты.

### Ограничения учебного деплоя

- Одна реплика Compose может давать простой при обновлении. Это не rolling/zero-downtime deployment.
- Ошибка `up --wait` делает job красной, но **не выполняет автоматический rollback**. Требуется отдельное восстановление.
- `resource_group` не даёт двум jobs одного окружения исполняться одновременно, но по умолчанию не гарантирует «самая новая версия последняя». Не запускай старый ручной production-job после более нового релиза; для реального процесса настрой предотвращение устаревших deployment jobs и правила очереди. [GitLab resource groups](https://docs.gitlab.com/ci/resource_groups/).
- Тег `SHA-pipelineID` уникален для pipeline, но retry `build_image` может его перезаписать. После staging не пересобирай образ этого релиза; для production-процесса применяй неизменяемые теги и продвижение digest.
- YAML-проверка не подтверждает доступность registry, credentials, SSH, Docker и healthcheck. Этот вариант не заявляется как успешно запущенный на реальных серверах.

## Откат, миграции и проверка результата

Перед выпуском сохрани ссылку на предыдущий рабочий **образ**, а не только commit. На соответствующем учебном сервере для отката используй реальную сохранённую ссылку; строка ниже — шаблон, который нужно заменить:

```bash
export APP_IMAGE='registry.example.com/team/app:previous-release'
export APP_ENV='production'
docker compose --project-name ci-demo -f /opt/ci-demo/compose.yaml \
  up -d --wait --wait-timeout 60
curl --fail http://127.0.0.1:8080/health
```

Это ручное повторное развёртывание предыдущего образа с прежним именем Compose project. Нужны существующий образ, права чтения и совместимая конфигурация. Никакой пересборки старого commit во время аварии: зависимости и base image могли измениться.

**Откат кода не откатывает данные.** Если миграция удалила колонку, старый контейнер не восстановит её содержимое. Используй совместимые этапы изменения схемы: сначала добавить новое, научить код работать с переходным состоянием, перенести данные, затем удалять старое после безопасного периода. Это дополнение к совету курса о backup. Восстановление backup тоже имеет время выполнения и риск потери более новых записей; процедуру нужно проверять заранее.

Healthcheck показывает заданную техническую готовность. После релиза наблюдают error rate, latency, нагрузку, логи и критичные бизнес-сценарии. Метрики сравнивают с ожидаемым уровнем; автоматический откат требует заданных порогов, окна наблюдения и реализации, не появляется от названия stage.

## Стратегии доставки из курса

| Стратегия | Как работает | Ограничение |
|---|---|---|
| Recreate | Остановить старую версию и запустить новую | Возможен простой; так устроен простой учебный случай |
| Rolling | Обновлять реплики постепенно | Временно работают разные версии; нужны совместимые API/схемы и проверки готовности |
| Blue-Green | Поднять второе окружение и переключить трафик | Дополнительная ёмкость; общая БД осложняет rollback |
| Canary | Дать новой версии малую долю трафика, сравнить метрики | Нужны маршрутизация и наблюдаемость; доля реплик не всегда равна доле запросов |
| Progressive rollout | Увеличивать охват по проверяемым этапам | Требуются условия продолжения, остановки и отката |

**Feature flag** включает поведение отдельно от deploy. Нужны стабильное распределение пользователей по группам, безопасное значение по умолчанию и удаление устаревших флагов. JSON-подобный блок и `featureFlags.isEnabled(...)` из курса — иллюстрация, а не готовая библиотека, автоматически реализующая проценты.

[[Kubernetes]], Istio и Prometheus/Grafana помогают реализовать эти сценарии, но не обязательны для любого Continuous Deployment. Автодеплой разумен только при достаточных проверках, контролируемом объёме изменения, наблюдении и понятном восстановлении. Ручной gate остаётся полезен при бизнес-окнах и требованиях конкретного процесса; универсальных юридических запретов по названию отрасли здесь не утверждается.

**GitOps:** CI собирает образ и обновляет желаемую версию в Git; Argo CD читает декларативную конфигурацию и применяет её в Kubernetes. CI тогда может не иметь production-kubeconfig. Sync и self-heal настраиваются явно, а доступ на изменение Git-манифестов фактически влияет на production. См. [Argo CD](../ArgoCD.md).

## Версионирование и релизная информация

Курс упоминает автоматические release notes и Semantic Versioning. SHA/pipeline ID отвечают за трассировку технической сборки; `MAJOR.MINOR.PATCH` сообщает о совместимости публичного API: несовместимое изменение, совместимое расширение, совместимое исправление. Версия `1.2.3` не вычисляется из Git автоматически: нужны соглашения о commits и отдельный инструмент/процесс. [Semantic Versioning](https://semver.org/).

Release notes связывают изменения, проверки, artifact и развёртывание. Удобно сохранять для релиза commit, pipeline, digest, конфигурационную версию и результат post-deploy проверок. Никаких credentials в release notes или artifacts.

## Безопасность pipeline

1. **Разделяй доверие.** MR из внешнего источника не должен исполняться рядом с production-ключами или на привилегированном build-хосте.
2. **Выдавай минимальные права.** Тестам не нужен доступ к деплою; серверу нужен pull, а не push в registry. Для staging и production нужны разные credentials.
3. **Проверяй исполняемый код.** Pipeline, зависимости, container images и удалённые скрипты — части цепочки поставки.
4. **Защищай выходные данные.** Логи, архивы, кэш и Docker layers могут сохранять секреты надолго. Не делай `COPY .env`, `echo "$TOKEN"`, `set -x` вокруг секретов.
5. **Ограничивай пути выпуска.** Защищённые ветки, review, полномочия на production и сериализация deploy защищают разные границы.
6. **Сохраняй возможность восстановления.** Версии artifacts, журналы действий, backup данных и план отката должны переживать неудачную job.

Команда курса `docker secret create` относится к Docker Swarm: это не универсальный способ передать секрет обычному `docker run`. А `ssh user@host` без удалённой команды не превращает следующие локальные строки в удалённый скрипт.

## Как отлаживать CI/CD

Начни с commit, pipeline ID, job и первой ошибочной команды. Затем найди уровень сбоя:

| Уровень | Симптом | Следующее действие |
|---|---|---|
| Конфигурация | Pipeline не создан / invalid config | CI Lint, YAML, `workflow` и job rules |
| Планирование | Pending / нет executor | Runner tags, protected refs, online status, лимиты |
| Подготовка | Pull/checkout failed | DNS, proxy, registry, credentials, диск |
| Выполнение | `command not found`, тест красный | Образ/runtime, lock-файл, cwd, первая ошибка теста |
| Передача результата | Нет `dist/` или archive expired | `artifacts:paths`, `needs`, срок хранения и источник artifact |
| Доставка | SSH/registry denied | Пользователь, host key, credential scope, права сервера |
| Работа приложения | Deploy прошёл, сервис не отвечает | Процесс, порт, healthcheck, конфигурация, сеть, логи |

Для воспроизведения запускай тот же commit, образ, команду и безопасные тестовые настройки. Сравни `node --version`, `npm --version`, `pwd`, наличие нужного файла. Не печатай всё окружение ради диагностики: оно может содержать secrets. Повтор job без выяснения причины скрывает flaky-тесты; автоматический retry допустим для обоснованно временного сбоя и повторяемой операции. [Диагностика GitLab](https://docs.gitlab.com/ci/debugging/).

## Что важно запомнить

Deploy завершён только после проверки работающего сервиса. Продвигай один artifact, меняй runtime-конфигурацию, ограничивай секреты и права. Ручная кнопка не равна безопасности, а красная deploy-job не равна автоматическому откату. Откат данных и приложения — разные процедуры.

## Проверка понимания

**Почему нельзя хранить токен в YAML?** Он попадёт в историю Git, клоны, review и резервные копии; удаление последним commit не отзывает уже раскрытый токен.

**Почему staging и production не должны просто стоять в одном stage?** Такие jobs могут стартовать параллельно. Для проверки staging до production нужна последовательность или явная зависимость.

**Почему сборка одного commit дважды может дать разные образы?** Могли измениться base image, зависимости, инструменты и входные параметры. Нужен уже проверенный artifact/digest.

**Почему приложение не видит переменную, заданную в CI?** Переменная доступна процессу job; её нужно отдельно передать удалённому процессу или контейнеру.

**Почему старый контейнер не гарантирует rollback после миграции?** Данные и схема уже могли измениться несовместимо. Откат кода не восстанавливает БД.

**Можно ли удалить `when: manual` и объявить процесс зрелым Continuous Deployment?** Автоматический выпуск появится, но достаточные проверки, мониторинг, контроль доступа и восстановление от этого не возникают.
