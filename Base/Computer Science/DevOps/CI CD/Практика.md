# Практика CI/CD

[Навигация](README.md) · Это **дополнительные упражнения** по механизмам [оригинального курса](../CI%20CD%20курс%20ориг.md). В исходнике есть фрагменты pipeline, но нет полного приложения и отдельных заданий с проверяемым результатом.

## Минимальный проект

В [examples/ci-demo](examples/ci-demo/package.json) находится небольшой HTTP-сервис на Node.js без сторонних зависимостей. Он нужен для сравнения CI-платформ, а не для изучения веб-фреймворка:

- `GET /health` → HTTP 200 и `{"status":"ok"}`.
- `GET /` → HTTP 200, сообщение и значение `APP_ENV` либо `development`.
- Неизвестный путь → HTTP 404.
- `npm test` запускает HTTP-сервер на случайном локальном порту и проверяет ответы, включая отрицательный сценарий 404.
- `npm run build` копирует приложение в `dist/`. Для этого интерпретируемого проекта build означает упаковку, а не компиляцию.

| Файл | Назначение |
|---|---|
| [app.cjs](examples/ci-demo/app.cjs) | HTTP-обработчик и запуск сервера на порту 3000 |
| [app.test.cjs](examples/ci-demo/app.test.cjs) | HTTP-проверка трёх маршрутов/исходов |
| [package.json](examples/ci-demo/package.json), [package-lock.json](examples/ci-demo/package-lock.json) | Команды npm и зафиксированное дерево зависимостей, здесь пустое |
| [.gitlab-ci.yml](examples/ci-demo/.gitlab-ci.yml) | События push/MR, test/build, artifacts и учебный cache |
| [Jenkinsfile](examples/ci-demo/Jenkinsfile) | Тот же проект через Docker agent, stages и архивирование |
| [Dockerfile](examples/ci-demo/Dockerfile), [.dockerignore](examples/ci-demo/.dockerignore) | Упаковка результата build, ограниченный build context |
| [compose.yaml](examples/ci-demo/compose.yaml) | Запуск опубликованного образа и healthcheck |
| [.gitignore](examples/ci-demo/.gitignore) | Исключение временных результатов, кэша и локального .env |

Это не production-сервис: нет TLS, аутентификации, БД и бизнес-логики. Эти возможности не нужны для проверки изучаемого пути доставки. Конфигурация не запускает CI для всей базы знаний: пример находится во вложенной директории.

## Локальная подготовка

Требуются Linux/POSIX shell, Node.js 22 и npm. Для установки здесь не нужны npm-пакеты из сети. Команды из корня базы знаний:

```bash
cd 'Computer Science/DevOps/CI CD/examples/ci-demo'
npm ci --no-audit --no-fund
npm run check
APP_ENV=test npm test
npm run build
node --check dist/app.cjs
tar -czf app.tar.gz -C dist app.cjs
tar -tzf app.tar.gz
```

Ожидается успешная синтаксическая и HTTP-проверка, затем файл `dist/app.cjs` и архив с `app.cjs`. `npm run check` — проверка синтаксиса, не линтер стиля. Для HTTP-теста требуется разрешение открывать localhost-порт. Если среда запрещает `listen`, это ограничение инфраструктуры, а не доказательство неправильного HTTP-ответа.

Для ручного просмотра запусти `APP_ENV=development npm start` и в другом терминале запроси `curl --fail http://127.0.0.1:3000/health`. Останови процесс через Ctrl+C. Процесс приложения слушает все интерфейсы; для сетевой изоляции используй учебную среду, а Docker-пример публикует порт только на localhost.

## Практика 1 — GitLab CI

Скопируй **все файлы, включая скрытые**, из `examples/ci-demo/` в корень отдельного учебного репозитория GitLab. Для первичного изучения используй только готовый CI, без production credentials. Нужен доступный runner с Docker executor; подробно — в [GitLab CI](GitLab%20CI.md).

1. Сделай push учебной ветки. Ожидаются `syntax` и `test`, после них `build`.
2. Открой MR. Ожидается MR pipeline. При следующем push source-ветки не должен добавиться второй branch pipeline для того же изменения.
3. Скачай artifact из build-job и проверь, что в архиве есть `app.cjs`. Файл должен происходить из выбранного pipeline.
4. В **копии учебного проекта** намеренно измени ожидаемый status в тесте с `ok` на другое значение. После push тест должен упасть, а build не должен стартовать. Верни изменение.
5. Удали кэш через интерфейс GitLab и повтори запуск. Результат должен остаться тем же. В этом проекте зависимостей нет, поэтому заметного ускорения от кэша не ожидается.

**Проверка понимания:** почему падение теста должно блокировать build именно в этом YAML? Потому что test-stage предшествует build, а `needs`, обходящего его, у build нет. Это свойство графа, не имени job.

## Практика 2 — передача артефакта

Добавь `verify` после `build` в `stages` и job `verify_package` из [GitLab-конспекта](GitLab%20CI.md). Она должна скачать artifact, вывести список архива и проверить синтаксис `dist/app.cjs`.

В учебной копии убери `dist/` из `artifacts:paths`. Архив ещё будет доступен, но проверка отдельного файла должна завершиться ошибкой: одинаковый checkout не восстанавливает результат build другой job. Верни настройку.

**Ожидаемый вывод:** файловая система job — не контракт обмена; передача необходимых файлов задаётся явно. Cache не должен скрывать ошибку отсутствующего release artifact.

## Практика 3 — Jenkins

На подготовленном Jenkins создай Pipeline from SCM с путём `Jenkinsfile`, доступом к учебному репозиторию и Docker-capable agent с label `docker`. Требуемые плагины перечислены в [конспекте Jenkins](Jenkins.md).

1. Выполни Build Now; должны последовательно пройти Test и Build, затем появиться `app.tar.gz` в artifacts сборки.
2. Повтори намеренную поломку теста. Ожидается ошибка Test, пропуск обычного Build и сообщение из `post failure`.
3. Настрой webhook **или** `pollSCM`; проверь автоматический запуск после изменения исходников. Сам Jenkinsfile не создаёт webhook.
4. Сравни граф с GitLab: в данном Jenkinsfile syntax и HTTP-проверки идут последовательно, а в GitLab — отдельными jobs одного stage.

**Проверка понимания:** если stage перенести на другой agent, почему `dist/` может исчезнуть? Он находился в workspace предыдущего узла. Нужно организовать передачу результата, а не надеяться на совпадение каталогов.

## Практика 4 — Docker и доставка

Сначала выполни локальные build/run/healthcheck из [Docker в CI/CD](Docker%20в%20CI%20CD.md). Затем, если есть отдельные учебные серверы, выполни шаги из [деплоя](Деплой%20и%20безопасность.md): публикация образа → staging → ручной production.

Условия готовности:

- Имена образа при build, push и deploy совпадают полностью.
- На обоих серверах используется образ одного pipeline, `APP_ENV` различается.
- Production ожидает успешный staging и ручное подтверждение.
- Неподготовленный SSH host key приводит к отказу подключения, а не к отключению проверки.
- Неуспешный healthcheck делает deploy-job красной; не заявляй автоматический rollback, которого в примере нет.
- Предыдущая версия сохранена в registry и может быть повторно развёрнута без пересборки.

**Проверка понимания:** почему не следует начинать лабораторную работу с настоящего production? Упражнение специально включает ошибочные тесты, проверки отказов и ручное восстановление; нужен отдельный стенд без пользовательских данных.

## Проверки при подготовке материалов

Фактические результаты проверки в рабочем пространстве:

- `npm ci` без сети и `npm run check` выполнены успешно на Node.js `v22.23.4`.
- HTTP-тест был запущен, но песочница запретила открытие порта: `listen EPERM` на `127.0.0.1`. Повтор вне песочницы не выполнен. **HTTP-поведение не заявляется как успешно протестированное.**
- Проверены заголовки, парность и языки code fences, 101 относительная ссылка/якорь в девяти документах CI/CD; ошибок не найдено. Примеры YAML разобраны с проверкой повторяющихся ключей, встроенные полные GitLab/Jenkins/Dockerfile-примеры совпадают с файлами проекта.
- `docker compose config --quiet` успешно проверил Compose с тестовыми значениями переменных. Для объединённого CI+CD-примера проверены ссылки на stages/jobs и порядок staging → production; 18 shell-фрагментов прошли `bash -n`/`sh -n`. Это проверка структуры, не исполнение GitLab rules.
- В отдельной временной копии успешно выполнены `npm run build`, `node --check dist/app.cjs`, упаковка и просмотр `app.tar.gz`; упакованный исходный файл соответствует результату build. Эти проверки не заменяют запуск приложения.
- GitLab CI Lint на сервере, Jenkins Declarative Linter, сборка Docker-образа, push в registry и SSH-деплой не выполнялись: соответствующие стенды и credentials не предоставлены. Команды даны с предпосылками, а не с вымышленным результатом запуска.

## Что изучить дальше для Junior

1. Отладка Linux-процессов, прав, DNS, TLS и SSH: ошибки pipeline часто происходят вне YAML. Используй [Linux Devops](../../OS/Linux/Linux%20Devops.md) и [конспект сетей](../Computer%20Networks.md).
2. Управление runners/agents: обновление, изоляция, лимиты CPU/RAM, очередь, ephemeral workers и недоверенный код.
3. Тестирование реального приложения с PostgreSQL: fixtures, миграции, контракты API и flaky-тесты.
4. Доставка неизменяемого artifact/digest, registry retention, совместимые миграции и репетиция rollback.
5. Секреты с ограниченным сроком жизни и правами, защита от supply-chain атак, сканирование зависимостей/образов.
6. [Kubernetes](../Kubernetes.md), health/readiness, rolling updates, затем [Argo CD](../ArgoCD.md) и GitOps. Эти документы пока служат планами дальнейшей практики.
7. [Prometheus](../Prometheus.md), [Grafana](../Grafana.md) и [Logging](../Logging.md): как заметить ухудшение после формально успешного deploy.
