# CI/CD — шпаргалка

[Навигация](README.md) · Основа: конструкции и команды из [курса](../CI%20CD%20курс%20ориг.md). Современные замены устаревшего синтаксиса помечены отдельно. Это указатель для повторения, а не самостоятельный production-pipeline.

## Понятия в одной таблице

| Понятие | Вспомнить |
|---|---|
| CI | Частая интеграция + автоматические проверки |
| Continuous Delivery | Готовность к выпуску; production может требовать решения человека |
| Continuous Deployment | Автоматический production после обязательных проверок |
| Pipeline | Один запуск графа работ |
| Stage | Логический этап; группировка зависит от платформы |
| GitLab job | Планируемая задача с командами |
| Jenkins step | Действие внутри `steps`, например `sh` |
| Runner / agent | Исполнитель; не сама задача |
| GitLab executor | Способ исполнения: Shell, Docker, Kubernetes и другие |
| Jenkins executor | Слот выполнения на узле |
| Artifact | Сохранённый результат конкретной работы |
| Cache | Необязательные данные для ускорения |
| Registry | Хранилище образов/версий |
| Environment | Целевая среда: dev, staging, production |
| Secret | Чувствительные credentials; выдаются по минимально нужным правам |
| Rollback | Возврат к предыдущему рабочему состоянию; данные требуют отдельного плана |

Путь изменения: **commit → событие push/MR → pipeline → test/build → artifact → deploy → проверки и мониторинг**. Build может предшествовать test, если тестируется собранный результат.

## GitLab CI: что означает запись

| Из курса | Назначение / нюанс |
|---|---|
| `.gitlab-ci.yml` | Обычно в корне репозитория |
| `stages: [test, build, deploy]` | Порядок этапов |
| `stage: test` | Этап данной job |
| `script: ['npm test']` | Команды job; нужен установленный runtime и проект |
| `image: node:…` | Среда job для поддерживающего executor; Node 16/18 из курса устарели |
| `variables: {NODE_ENV: test}` | Несекретная настройка; в процессе будет строка |
| `artifacts: {paths: [dist/]}` | Сохранить результат относительно рабочей директории |
| `cache: {paths: [node_modules/]}` | Пример курса; для `npm ci` обычно полезнее `.npm/` |
| `needs: [build]` | Ждать указанную job; проверить, не обошли ли остальные проверки |
| `services: [postgres:15, redis:7]` | Соседние сервисы; клиент и готовность проверяются отдельно |
| `environment: {name: staging}` | Метаданные окружения, не provision сервера |
| `when: manual` | Ручной старт job; для обязательного gate задать `allow_failure: false` |
| `only: [main]` / `except` | Старые условия из курса; для нового YAML применять `rules` |
| `$CI_COMMIT_SHA` | Идентификатор commit; не digest образа |

**Актуализация:** `default:image`, `workflow:rules`, `rules`, `expire_in`, `cache:key:files`, `needs:artifacts` и `resource_group` разобраны в [GitLab CI](GitLab%20CI.md) и [деплое](Деплой%20и%20безопасность.md). Это уточнения сверх минимальных примеров курса, а не повод запоминать все ключи сразу.

## Jenkins: каркас и директивы

```groovy
pipeline {
    agent any
    stages {
        stage('Check') {
            steps {
                echo 'Pipeline started'
            }
        }
    }
    post {
        failure {
            echo 'Inspect the failing step'
        }
    }
}
```

Этот самостоятельный каркас только выводит сообщение. Он запускается через настроенную Jenkins job (например, Build Now), требует доступного agent и ничего не тестирует/деплоит. Рабочий пример приложения — в [Jenkins](Jenkins.md).

| Конструкция курса | Значение |
|---|---|
| `agent any` / `agent none` | Выделить любой подходящий узел / назначать agents по stages |
| `agent { label 'linux' }` | Выбор agent по метке |
| `agent { docker { image '…' } }` | Docker Pipeline; нужны плагин, daemon и agent |
| `steps { sh 'npm test' }` | Запустить shell-команду; ненулевой exit code обычно прерывает обычный путь |
| `environment { APP_NAME = 'my-app' }` | Переменные окружения |
| `credentials('credential-id')` | Выдать credential по ID, не хранить пароль в Jenkinsfile |
| `post { success { … } failure { … } }` | Действия по итоговому состоянию |
| `timeout(time: 1, unit: 'HOURS')` | Ограничение времени |
| `retry(3)` | Повтор; опасен вокруг неповторяемых операций |
| `timestamps()` | Метки времени; нужен Timestamper plugin |
| `cron('H 4 * * 1-5')` | Расписание в выбранную минуту 4-го часа по будням |
| `pollSCM('H/5 * * * *')` | Периодический поиск изменений SCM |
| `parameters` | `string`, `choice`, `booleanParam`; валидировать перед shell |
| `reuseNode true` | Для Docker stage использовать текущий узел/workspace |

## Команды из курса

Команды ниже описаны в контексте: наличие команды в таблице не означает, что её можно выполнить без настройки среды.

| Команда | Когда и зачем |
|---|---|
| `git push origin develop` | Передать ветку; pipeline создаётся, если это разрешено правилами |
| `git push origin main` | Передать основную ветку; не заменяет review/защиту ветки |
| `npm install` | Разработка и обновление зависимостей |
| `npm ci` | CI-установка по согласованным package.json и lock-файлу |
| `npm test` | Запуск script `test` из package.json |
| `npm run build` | Запуск script `build`; команда не существует сама по себе без проекта |
| `npm run test:integration` / `npm run test:e2e` | Scripts должны быть определены в конкретном проекте |
| `pip install -r requirements.txt` | Установка Python-зависимостей; файл должен существовать |
| `pytest tests/` | Нужны pytest, тесты и зависимости проекта |
| `docker build -t "$IMAGE" .` | Создать образ из Dockerfile и контекста |
| `docker push "$IMAGE"` | Опубликовать то же полное имя после login |
| `docker pull "$IMAGE"` | Скачать образ на целевом сервере с правами чтения |
| `docker run -d "$IMAGE"` | Создать новый контейнер; не обновляет существующий сам по себе |
| `ssh user@host 'command'` | Выполнить конкретную команду удалённо; проверить ключ хоста |
| `scp app.zip user@host:/path/` | Скопировать artifact, но ещё не запустить приложение |
| `rsync` | Синхронизация файлов; внимательно выбирать источник, назначение и параметры удаления |
| `kubectl apply -f k8s/` | Применить manifests; нужны кластер, context и права, готовность проверяется отдельно |
| `kubectl set image deployment/myapp myapp="$IMAGE"` | Обновить образ уже существующего Deployment/container с указанными именами |
| `docker system prune` | Удаление неиспользуемых ресурсов; сначала оценить влияние на общий runner |
| `docker secret create db_pass -` | Создать Swarm secret из stdin; это не механизм обычного docker run |

`./deploy.sh` и `./check_deployment_health.sh` в оригинале — имена отсутствующих реализаций. Нельзя считать их рабочими командами, пока сами файлы и их зависимости не созданы.

## Быстрая диагностика

- **Pipeline отсутствует:** YAML → `workflow` → событие/ref.
- **Job pending:** runner/agent → tags/label → права → свободные ресурсы.
- **Падение команды:** первая ошибка → exit code → commit → runtime/зависимости.
- **Нет artifact:** путь → загрузка → зависимости → срок хранения.
- **Docker/SSH denied:** endpoint → credential scope → права; не печатать секреты.
- **Deploy зелёный, приложение не работает:** healthcheck → порт → конфигурация → логи → пользовательский сценарий.

## Пять вопросов перед выпуском

1. **Что выпускаем?** Конкретный проверенный artifact/digest, связанный с commit и pipeline.
2. **Где он уже проверен?** Staging и нужные тесты именно этой версии.
3. **Кто может разрешить и выполнить deploy?** Права и protected-настройки, а не только кнопка.
4. **Как узнаем об ошибке?** Healthcheck, метрики, логи и ответственный.
5. **Как восстановимся?** Предыдущий artifact, совместимость данных и проверенная процедура.
