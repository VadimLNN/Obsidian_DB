# Docker Best Practices

> [!summary] Основная идея
> Хороший Docker-образ содержит **только необходимое для работы приложения**, эффективно использует **кэш сборки**, легко обновляется и имеет **минимальную поверхность атаки**.

## 1. Multi-stage builds — разделяйте сборку и запуск

**Проблема:** компилятор, SDK, инструменты сборки и исходники нужны для получения артефакта, но часто не нужны работающему приложению. Если оставить их в финальном образе, увеличатся его размер и количество компонентов, требующих обновления.

**Решение:** использовать несколько этапов (`FROM ... AS ...`) и переносить в финальный этап только необходимые артефакты через `COPY --from=...`.

```text
┌─────────────────────────────┐
│ builder                     │
│ Go SDK + исходники          │
│ Компиляция → /out/app       │
└──────────────┬──────────────┘
               │ COPY --from=builder
               ▼
┌─────────────────────────────┐
│ runtime                     │
│ Только бинарный файл        │
└─────────────────────────────┘
```

**Обычный Dockerfile для [[Go]]:**

```dockerfile
FROM golang:1.27
WORKDIR /app
COPY . .
RUN go build -o app .
CMD ["/app/app"]
```

В таком варианте финальный образ содержит Go SDK и файлы, попавшие в образ при `COPY`.

**Multi-stage вариант:**

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.27-alpine AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux \
    go build -trimpath -ldflags="-s -w" -o /out/app .

FROM scratch
COPY --from=builder /out/app /app
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["/app"]
```

- `builder` — этап компиляции; его файловая система **не входит в итоговый образ**, если не копировать из неё данные явно.
- `CGO_ENABLED=0` позволяет собрать Go-приложение без зависимости от C-библиотек (если код и зависимости поддерживают такой режим).
- `scratch` — пустой базовый образ, подходящий для автономного статического бинарного файла.
- `USER 65532:65532` — запуск от непривилегированного пользователя.

> [!warning] Ограничения `scratch`
> Внутри нет оболочки, пакетного менеджера, системных сертификатов CA и прочих привычных файлов. Для HTTPS-клиента, работы с часовыми поясами, динамической линковки и других требований понадобятся дополнительные файлы или другой runtime-образ (например, distroless либо Alpine). Multi-stage применим не только к Go, но и к Java, Node.js, Python — просто содержимое runtime-этапа будет другим.

**Итог:** меньший образ обычно быстрее передаётся через сеть и занимает меньше места в registry. Уменьшение количества компонентов может снизить поверхность атаки, но **не гарантирует отсутствие уязвимостей** или ускорение запуска приложения.

## 2. Оптимизируйте слои, а не их количество любой ценой

Файловые инструкции `RUN`, `COPY`, `ADD` формируют изменения файловой системы образа. Если создать файлы в одном слое и удалить в другом, их содержимое может продолжать занимать место в нижнем слое.

**Неудачно:**

```dockerfile
RUN apt-get update
RUN apt-get install -y ca-certificates
RUN rm -rf /var/lib/apt/lists/*
```

**Лучше:**

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates \
    && rm -rf /var/lib/apt/lists/*
```

Что изменилось:

- Установка и очистка выполняются **в одном `RUN`**, поэтому кэш `apt` не сохраняется в итоговом слое.
- `--no-install-recommends` исключает необязательные рекомендуемые пакеты.
- `apt-get update` и `apt-get install` находятся вместе, чтобы не использовать устаревший индекс пакетов из отдельного кэшированного шага.

**Важное уточнение:** меньше слоёв ≠ автоматически меньше размер или быстрее сборка. Имеет смысл объединять **связанные действия**, но не сливать весь Dockerfile в одну огромную команду: отдельные шаги часто лучше кэшируются и проще отлаживаются.

## 3. Размещайте редко меняющиеся инструкции раньше

Docker/BuildKit переиспользует результаты предыдущих операций, пока их входные данные и условия не изменились. Если сначала скопировать весь исходный код, любое изменение исходников может привести к повторной установке зависимостей.

**Плохо для кэша:**

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
```

**Лучше:**

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

Теперь изменение `.py`-файлов обычно не затрагивает кэш слоя установки зависимостей: `requirements.txt` копируется отдельно и меняется реже.

**Типичный порядок:** базовый образ → системные зависимости → манифесты зависимостей (`go.mod`, `requirements.txt`, `package-lock.json`) → установка зависимостей → исходники → сборка.

> [!tip] BuildKit cache mounts
> В долгих сборках кэш скачанных зависимостей можно сохранять между сборками без включения его в слой образа:
>
> ```dockerfile
> RUN --mount=type=cache,target=/root/.cache/go-build \
>     go build -o /out/app .
> ```
>
> Содержимое cache mount — ускоритель, а не обязательная часть воспроизводимой сборки.

## 4. Исключайте мусор из контекста сборки

Файл `.dockerignore` не даёт ненужным файлам попасть в build context и в область действия `COPY . .`.

```dockerignore
.git
.venv
__pycache__/
.pytest_cache/
node_modules/
*.log
.env
.env.*
```

Это уменьшает объём передаваемых данных, сокращает лишние срабатывания кэша и снижает вероятность случайно добавить локальные файлы в образ.

**Секреты не должны попадать в образ:** `.dockerignore` — полезная страховка, но для сборочных секретов используйте механизмы BuildKit secrets, а для runtime — предусмотренное системой управление секретами. Не передавайте пароли через `ARG`/`ENV` в Dockerfile.

## 5. Дополнительные практики для production

- **Фиксируйте версии базовых образов.** Предпочитайте `python:3.13-slim` вместо `python:latest`. Для строгой воспроизводимости фиксируйте digest (`@sha256:...`), но планируйте регулярное обновление.
- **Обновляйте и проверяйте образы.** Маленький образ тоже может содержать уязвимости. Нужны пересборки с патчами, сканирование зависимостей и проверка в CI.
- **Запускайте приложение не от root**, если повышенные привилегии не требуются (`USER`).
- **Не ставьте в runtime лишние утилиты**, включая компиляторы, отладчики и средства администрирования, если они не нужны приложению.
- **Разделяйте сервисы по ответственности.** Приложение, база данных и прокси обычно должны иметь собственные контейнеры; постоянные данные храните вне эфемерной файловой системы контейнера.

## Краткий чек-лист

- [ ] Компиляция и запуск разделены через multi-stage там, где это полезно.
- [ ] В runtime нет ненужных SDK, исходников и инструментов сборки.
- [ ] Установка пакетов и очистка временных файлов происходят в одном `RUN`.
- [ ] Редко меняющиеся зависимости идут раньше часто меняющегося кода.
- [ ] Настроен `.dockerignore`; секреты не попадают в образ.
- [ ] Базовые образы фиксированы по версии и регулярно обновляются.
- [ ] Приложение запускается без root-привилегий, если это возможно.
- [ ] Образ проверяется на уязвимости и тестируется в CI.
