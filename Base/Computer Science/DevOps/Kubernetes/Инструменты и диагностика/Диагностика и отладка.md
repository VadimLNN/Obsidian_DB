# Диагностика и отладка

[[Kubernetes|Карта тем]] · [[kubectl]] · [[Дополнительные инструменты]]

## Последовательность поиска причины

Сначала определяются context, namespace, объект и первая конкретная ошибка. Проблемы scheduler, загрузки image, запуска процесса и сетевого доступа требуют разных действий.

| Симптом | Проверка | Возможная причина |
|---|---|---|
| Pod Pending | `describe pod`, events, Nodes | Недостаточно requests-capacity, ограничения размещения, неготовое хранилище |
| ImagePullBackOff / ErrImagePull | Events, имя image, registry credentials | Нет тега, нет доступа, DNS/сеть или несовместимая платформа |
| CrashLoopBackOff | Текущие/previous logs, last state | Ошибка команды, конфигурации, OOM, провал liveness/startup |
| Running, но не Ready | Probes и application logs | Старт не завершён, неправильный endpoint/порт, зависимость недоступна |
| [[Service]] без backend | Selector, labels, namespace, EndpointSlice | Нет подходящих или ready Pod |
| Имя не разрешается | DNS из Pod | Неправильное имя/namespace, CoreDNS, DNS policy или блокировка сети |
| [[Ingress]] отвечает 404/502/503 | Controller, class, rules, Service и endpoints | Host/path не совпал, backend недоступен, неверный порт |
| Ошибка Forbidden | Identity, RBAC, namespace | Не хватает прав; повтор apply права не добавляет |

`CrashLoopBackOff` — состояние ожидания повторного запуска с задержкой, а не самостоятельная причина ошибки.

## Базовые команды

```bash
kubectl config current-context
kubectl -n example-app get pods -o wide
kubectl -n example-app get events --sort-by=.metadata.creationTimestamp
kubectl -n example-app describe pod example-pod
kubectl -n example-app logs example-pod -c web
kubectl -n example-app logs example-pod -c web --previous
kubectl -n example-app describe service example-service
kubectl -n example-app get endpointslices -l kubernetes.io/service-name=example-service
```

Имена заменяются существующими объектами. Сначала читается первая причина в events/логах, затем проверяется конфигурация. Restart без понимания причины может стереть полезный контекст и временно скрыть неисправность.

При сетевом сбое отдельно проверяются DNS, TCP-соединение, HTTP route, Host и поведение приложения. Для внутрикластерного запроса полезен диагностический curl-Pod из [[DNS и Service Discovery]].

## Минимальный образ без инструментов

В production-образе может не быть shell, `ip`, `ping`, `curl` или `netstat`. Это не причина постоянно устанавливать диагностические пакеты в работающий контейнер: такие изменения невоспроизводимы и исчезают при замене.

### Сторонний kubectl-debug

Внешний инструмент [aylei/kubectl-debug](https://github.com/aylei/kubectl-debug) использовал debug-agent и дополнительные контейнеры для работы в namespaces целевого контейнера. Это не обычное добавление постоянного sidecar в Deployment template.

Историческая форма команды сохранена с нейтральным именем образа:

```bash
kubectl-debug example-pod --agentless=true --port-forward=true \
  --agent-image=registry.example.com/demo/debug-agent:v0.1
```

Образ — **заглушка**, требуется собственный совместимый debug-agent; flags и права зависят от версии внешней утилиты. Имя Pod относится к выбранному context/namespace, а не создаётся командой.

> [!warning] Статус инструмента
> Репозиторий `aylei/kubectl-debug` явно помечен как больше не сопровождаемый. Этот пример сохраняет технический контекст, но не выдаётся за актуальную универсальную инструкцию установки. Возможность отладки зависит от runtime, безопасности узла, привилегий и доступности image registry.

### Встроенный kubectl debug

Современный вариант — встроенный `kubectl debug` с ephemeral container. Пример для существующего `example-pod` с контейнером `web`:

```bash
kubectl -n example-app debug -it example-pod --image=busybox:1.37 --target=web
```

Это дополнение к старому инструменту, а не переименование его flags. Требуются разрешение на ephemeral containers, подходящая версия и runtime. BusyBox предоставляет базовые утилиты, но не гарантирует наличие curl. Поддержка `--target` не означает автоматический доступ ко всем файлам и процессам целевого контейнера. [Отладка работающих Pod](https://kubernetes.io/docs/tasks/debug/debug-application/debug-running-pod/).

## Карта диагностики и ограничения

[Troubleshooting Deployments — Learnk8s](https://learnk8s.io/troubleshooting-deployments) — внешняя карта последовательной проверки Deployment → Pod → Service → Ingress. В исходном материале была ссылка на карту, а не встроенное изображение; ссылка сохранена.

В выводе `describe`, YAML, логах и core dumps могут быть чувствительные данные. Перед публикацией диагностического вывода исключаются credentials и данные пользователей. Не следует лечить сетевую проблему снятием всех ограничений RBAC, security groups или NetworkPolicy.
