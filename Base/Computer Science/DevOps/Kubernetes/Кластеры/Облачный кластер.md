# Облачный кластер

[[Kubernetes|Карта тем]] · [[Self-hosted и Managed Kubernetes]] · [[Ingress]]

## Yandex Managed Service for Kubernetes

Yandex Cloud предоставляет управляемый Kubernetes с интеграциями сети, балансировщиков, мониторинга и других облачных сервисов. Кластером можно управлять через консоль, `yc`, API и инструменты IaC, включая Terraform. Marketplace предоставляет готовые приложения для установки.

![](https://ucarecdn.stepik.net/53cdeb03-23ee-43ec-a123-8a9b8c96083f/)

Cluster Autoscaler изменяет число Nodes, когда размещение workloads требует дополнительной ёмкости или позволяет убрать узлы. Это отличается от HPA, меняющего количество Pod; «автоматически увеличивать Nodes по любой нагрузке CPU» — неточное обобщение.

## Создание control plane

Ресурсы создаются в выбранном каталоге облака с нужными IAM-правами и сетью. В [консоли](https://console.yandex.cloud/) сервис Managed Service for Kubernetes содержит создание кластера:

![](https://ucarecdn.stepik.net/aa6e91ab-2f40-4190-bc40-70d9917050d5/)

Параметры кластера включают расположение, версию, доступ к API и сетевые настройки:

![](https://ucarecdn.stepik.net/f56a4a84-d46f-451c-8027-82d5f459129a/)

Состояние `Healthy` означает готовность управляющих компонентов по критериям сервиса. Оно не означает наличие worker nodes или готовность приложения. Оценка создания порядка десяти минут — ориентир конкретного сценария, не гарантия.

> [!warning] Публичный доступ и security groups
> Широкое разрешение входящего/исходящего трафика не должно переноситься как безопасная настройка по умолчанию. Для API, Nodes, probes балансировщика и внешних сервисов нужны конкретные разрешённые направления. Поведение группы по умолчанию зависит от текущей конфигурации сети. [Настройка security groups](https://yandex.cloud/ru/docs/managed-kubernetes/operations/connect/security-groups) — ссылка на документацию провайдера; при проверке материала страница не ответила, поэтому конкретные актуальные правила здесь не воспроизводятся.

## Подключение через yc и kubeconfig

Установка `yc` выполняется по [инструкции CLI](https://yandex.cloud/ru/docs/cli/quickstart#install). Для профиля с нужными правами:

```bash
yc init
```

![](https://ucarecdn.stepik.net/d280ed7c-a026-407e-851d-935a92eefc41/)

Данные подключения доступны в карточке кластера:

![](https://ucarecdn.stepik.net/d2f7f8a9-126a-43fd-baa7-26d673d95979/)

```bash
CLUSTER_ID='replace-with-actual-cluster-id'
yc managed-kubernetes cluster get-credentials --id "$CLUSTER_ID" --external
kubectl config current-context
kubectl get namespaces
```

`CLUSTER_ID` заменяется реальным идентификатором. `--external` требует настроенного и достижимого внешнего endpoint. Команда записывает сведения о context в kubeconfig; необходимо проверить текущий context перед следующими операциями.

Для обычного пользовательского способа аутентификация может зависеть от `yc` и его профиля. Файл kubeconfig не всегда является самодостаточным статическим credential. Для автоматизации выбирается отдельно поддерживаемая модель доступа и минимальные права. [Подключение к кластеру](https://yandex.cloud/ru/docs/managed-kubernetes/operations/connect/).

Типичные системные namespaces в таком кластере: `default`, `kube-node-lease`, `kube-public`, `kube-system`, `yandex-system`. Набор и состояние зависят от установки.

## Группа worker nodes

После создания control plane нужна группа узлов для обычных workloads. В карточке кластера доступен раздел управления узлами:

![](https://ucarecdn.stepik.net/f2f20d7a-f8db-450a-9098-317588f7b82c/)

Пример параметров небольшой **демонстрационной** группы, не sizing для production:

| Параметр | Значение/условие |
|---|---|
| Имя | `example-pool` |
| Версия | Поддерживаемая совместимая с control plane |
| Масштабирование | Фиксированная группа из 1 Node |
| Вычислительные ресурсы | Standard, 2 vCPU, 4 ГБ RAM |
| Диск | HDD, 96 ГБ как исходная демонстрационная конфигурация |
| Расположение | Пример зоны `ru-central1-a` и соответствующая существующая subnet |
| Публичный IP | В демонстрации назначался автоматически; для эксплуатации выбирается осознанно |
| Security groups | Явно определённые правила вместо переноса настройки «без групп» |
| SSH user | `admin`, если нужен такой способ доступа |
| SSH key | Публичная часть ключа оператора |
| Окно обновления | Согласованное maintenance window; «в любое время» подходит не каждому workload |

Создание ключа и чтение **публичной** части, если подходящего ключа ещё нет:

```bash
ssh-keygen -t ed25519
cat ~/.ssh/id_ed25519.pub
```

Существующий ключ не перезаписывается без необходимости; private key не загружается в форму публичного SSH-ключа.

```bash
kubectl get nodes
kubectl get nodes -o wide
```

У Node ожидается `Ready`. Конкретные имя, IP и версия генерируются выбранной инфраструктурой; старые значения вроде `v1.30.1` в снимке вывода не являются требованием к новой установке. Отсутствие Nodes оставляет обычные Pod без места для запуска.

## Доступ к приложениям

Для приложения отдельно создаются Deployment/Pod и [[Service]]. Тип LoadBalancer может задействовать облачный балансировщик; [[Ingress]] объединяет HTTP(S)-маршруты через контроллер. Публичный API endpoint, IP Node и IP приложения — разные адреса и разные границы доступа.

Создание ресурсов тарифицируется по правилам облака. Одна Node не обеспечивает отказоустойчивость приложения. Диагностика развёртывания, readiness и достаточность ресурсов остаются ответственностью команды. [Ресурсы Managed Kubernetes](https://yandex.cloud/ru/docs/managed-kubernetes/concepts/).
