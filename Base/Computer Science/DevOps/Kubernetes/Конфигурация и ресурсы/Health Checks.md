# Health Checks

[[Kubernetes|Карта тем]] · [[Pod]] · [[Service]] · [[Стратегии обновления]]

## Три вида probes

Probes — проверки состояния контейнера, выполняемые kubelet. Они различают «процесс жив», «приложение готово принимать трафик» и «запуск завершён».

| Проверка | Вопрос | Последствие устойчивой ошибки |
|---|---|---|
| `livenessProbe` | Способно ли приложение продолжать работу без перезапуска? | Завершение контейнера и возможный restart согласно restartPolicy |
| `readinessProbe` | Готово ли приложение обслуживать запросы сейчас? | Pod становится неготовым для обычной маршрутизации Service; restart не выполняется |
| `startupProbe` | Закончен ли длительный старт? | Пока не успешна, liveness/readiness не выполняются; исчерпание попыток ведёт к завершению контейнера |

Проверки должны отражать состояние конкретного приложения. Проблема внешней БД не всегда лечится рестартом всех клиентов; включение такой зависимости в liveness может усилить аварию.

## HTTP liveness

`liveness.yaml` использует диагностический образ из официального примера вместо старого `k8s.gcr.io/liveness`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: liveness-http
  namespace: default
  labels:
    test: liveness
spec:
  containers:
    - name: liveness
      image: registry.k8s.io/e2e-test-images/agnhost:2.40
      args: ["liveness"]
      ports:
        - name: liveness-port
          containerPort: 8080
      livenessProbe:
        httpGet:
          path: /healthz
          port: liveness-port
        initialDelaySeconds: 3
        periodSeconds: 2
```

В этом демонстрационном обработчике `/healthz` намеренно начинает возвращать 500 после периода успешной работы. Рост `RESTARTS` ожидаем; это не образ production-приложения. HTTP-коды **200–399** считаются успешными, а не только 200. [Официальный пример HTTP liveness](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/#define-a-liveness-http-request).

```bash
kubectl apply -f liveness.yaml
kubectl -n default get pod liveness-http --watch
kubectl -n default describe pod liveness-http
```

## Параметры

| Поле | Назначение | По умолчанию |
|---|---|---|
| `initialDelaySeconds` | Задержка перед началом проверок контейнера | 0 |
| `periodSeconds` | Период проверок | 10 секунд |
| `timeoutSeconds` | Время ожидания выполнения одной проверки | 1 секунда |
| `failureThreshold` | Число последовательных неудач до реакции | 3 |
| `successThreshold` | Последовательные успехи для восстановления после неудачи | 1; для liveness/startup должно быть 1 |

> [!note] Время реакции
> Нельзя точно вывести «рестарт спустя 9 секунд» простым сложением трёх параметров. Влияют положение сбоя между проверками, их длительность, число последовательных неудач, задержка завершения и restart backoff. Initial delay относится к старту контейнера, а не добавляется заново при каждом зависании.

## Exec readiness

Фрагмент **конкретного контейнера**, а не самостоятельный манифест:

```yaml
readinessProbe:
  exec:
    command:
      - cat
      - /tmp/healthy
  initialDelaySeconds: 5
  periodSeconds: 5
```

Команда выполняется внутри контейнера. Exit code 0 означает успех; отсутствие/нечитаемость файла приводит к ошибке. Приложение или init/entrypoint-логика должны поддерживать `/tmp/healthy`; Kubernetes не создаёт этот файл автоматически. В минимальном образе также должна существовать команда `cat`.

Readiness может временно исключить перегруженный экземпляр из обычных ready endpoints, если проверка действительно отражает его способность обслуживать запросы. Она не переносит уже начатый запрос на другой Pod и не измеряет нагрузку автоматически. Неготовность не равна гарантированному обрыву всех существующих соединений.

## Startup probe

Для приложения с долгим стартом агрессивная liveness может запускать бесконечный цикл рестартов. Startup probe даёт время на инициализацию, не отключая проверку зависшего запуска.

Фрагмент контейнера с именованным портом `liveness-port` и работающим `/healthz`:

```yaml
startupProbe:
  httpGet:
    path: /healthz
    port: liveness-port
  failureThreshold: 30
  periodSeconds: 10
```

Настройка задаёт примерно пятиминутный бюджет проверок запуска. После первого успеха startup probe уступает работу обычным liveness/readiness. Этот фрагмент предназначен для реального медленно стартующего приложения; без осмысления его не нужно добавлять к диагностическому серверу, который намеренно ломается через десять секунд.

## Практические ограничения

Endpoints должны быть лёгкими, иметь ясную семантику и не изменять данные. Слишком короткий timeout при CPU throttling способен вызвать ложные ошибки. Слишком общая readiness может одновременно исключить все replicas; слишком агрессивная liveness — перезапустить весь сервис.

Readiness и startup помогают rollout, но не заменяют внешний smoke-тест и мониторинг пользовательского сценария. Пробы и ресурсные ограничения проектируются вместе с разработчиками приложения. См. [[Requests, Limits и QoS]] и [[Диагностика и отладка]].
