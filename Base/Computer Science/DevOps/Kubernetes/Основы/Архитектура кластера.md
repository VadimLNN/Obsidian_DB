# Архитектура кластера

[[Kubernetes|Карта тем]] · [[Обзор Kubernetes]] · [[Pod]]

## Control Plane и Data Plane

**Control Plane** управляет состоянием кластера и принимает решения. **Data Plane** обеспечивает выполнение контейнеров и передачу трафика на узлах. Это функциональное разделение, а не обязательное распределение по разным физическим машинам.

## Компоненты Control Plane

### kube-apiserver

API server — центральная точка взаимодействия с Kubernetes API. [[kubectl]], контроллеры, scheduler и kubelet получают и изменяют состояние через API. Запросы проходят аутентификацию, авторизацию, admission и проверку допустимости объекта. Принятие объекта API не означает, что контейнер уже запущен.

![[Pasted image 20261110171653.png]]

### kube-scheduler

Scheduler выбирает узел для Pod, которому ещё не назначена Node. При выборе учитываются requests ресурсов и ограничения размещения. Он фиксирует назначение; непосредственно контейнеры запускает kubelet через runtime. Если подходящего узла нет, Pod остаётся Pending; причины отражаются в events.

### kube-controller-manager

Controller manager запускает контроллеры, каждый из которых наблюдает за относящимися к нему объектами и приближает текущее состояние к желаемому. Например, Deployment controller управляет ReplicaSet, а ReplicaSet controller — количеством Pod. Контроллеры получают изменения через API, а не редактируют etcd напрямую.

### etcd

**etcd** — отдельный открытый проект распределённого key-value хранилища. Kubernetes сохраняет в нём API-объекты, конфигурацию и состояние кластера. Потеря этого хранилища нарушает работу control plane, поэтому важны доступность, резервное копирование и проверка восстановления.

> [!warning] Граница резервной копии
> Snapshot etcd не содержит автоматически данные PersistentVolume, внешних БД, container registry и всех файлов конфигурации узлов. Для восстановления платформы нужны также соответствующие данные, сертификаты и конфигурация. Утверждение «одной копии etcd достаточно для всего кластера» неполно. [Эксплуатация и восстановление etcd](https://kubernetes.io/docs/tasks/administer-cluster/configure-upgrade-etcd/).

### Cloud Controller Manager

В облачных интеграциях cloud-controller-manager связывает Kubernetes с API провайдера, например для узлов и балансировщиков. Конкретный состав control plane зависит от реализации. Перечень «пять бинарников» — упрощённое перечисление основных процессов, а не полное описание работающего кластера.

## Компоненты узла

| Компонент | Ответственность |
|---|---|
| **kubelet** | Наблюдение за назначенными Pod, запуск контейнеров через runtime, [[Health Checks|probes]] и передача статуса |
| **Container runtime** | Получение образов и выполнение контейнеров; например containerd или CRI-O через CRI |
| **kube-proxy** | Реализация правил доступа к [[Service]] в поддерживаемых сетевых режимах |

Runtime и kubelet нужны не только на worker-узлах: на control-plane узлах kubelet может запускать управляющие компоненты как static Pods. Роли на диаграмме отражают назначение компонентов.

> [!note] Сеть и runtime
> kube-proxy не является полной сетевой системой Kubernetes: Pod network обеспечивает CNI-реализация, а некоторые реализации также заменяют kube-proxy. Историческая интеграция с [[Docker]] через dockershim не равнозначна современному требованию CRI. Docker-образы продолжают использоваться и с containerd.

## Путь от манифеста до контейнера

```text
kubectl apply
      ↓
kube-apiserver → сохранённое желаемое состояние в etcd
      ↓
Deployment controller → ReplicaSet controller → Pod
      ↓
scheduler → назначение Pod на Node
      ↓
kubelet → container runtime → контейнеры
      ↓
status и события через API; следующий цикл reconciliation
```

Контроллеры работают непрерывно. Удаление управляемого Pod создаёт расхождение с желаемым количеством, после чего появляется новый Pod. Это новый объект, а не перемещение старого контейнера на другую машину.

Документация: [архитектура Kubernetes и её варианты](https://kubernetes.io/docs/concepts/architecture/). Права, storage, CNI и HA требуют отдельных настроек; их подробные реализации не выводятся из одной архитектурной схемы.
