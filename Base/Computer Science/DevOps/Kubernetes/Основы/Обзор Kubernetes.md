# Обзор Kubernetes

[[Kubernetes|Карта тем]] · [[Архитектура кластера]] · [[Управление ресурсами]]

## Назначение

**Kubernetes (K8s)** — система оркестрации контейнеризированных приложений. Через API задаётся желаемое состояние: какие приложения должны работать, сколько экземпляров требуется, как организованы конфигурация, сеть и ресурсы. Контроллеры приводят наблюдаемое состояние к заданному.

![](https://ucarecdn.stepik.net/f0ca44ca-8e4c-4203-9eea-c75f3987baf1/)

Проект открыт Google в 2014 году; на его архитектуру повлиял опыт эксплуатации внутренней системы Borg. Название происходит от греческого слова «рулевой».

![Кубернетес](https://ucarecdn.stepik.net/3abc969c-7328-4435-a43f-39f596d76283/)

Минимальная планируемая единица — [[Pod]], содержащий один или несколько связанных контейнеров. Pod назначается на Node. Набор узлов и управляющих компонентов образует кластер; API позволяет управлять им единообразно, независимо от конкретной машины приложения.

## Возможности

| Задача | Механизм |
|---|---|
| Развёртывание контейнеров | Pod и контроллеры рабочих нагрузок |
| Поддержание количества экземпляров | [[Deployment и ReplicaSet]] |
| Масштабирование | Изменение replicas; при отдельной настройке — автомасштабирование |
| Планирование CPU/RAM и ограничения | [[Requests, Limits и QoS]] |
| Стабильный доступ и распределение соединений | [[Service]], [[DNS и Service Discovery]] |
| HTTP(S)-маршрутизация | [[Ingress]] и установленный контроллер |
| Проверка состояния и восстановление | [[Health Checks]], restart policy и контроллеры |
| Обновление и откат приложения | [[Стратегии обновления]] |
| Управление доступом | RBAC и ServiceAccount; отдельная настройка политик |
| Сетевые ограничения | NetworkPolicy при поддержке сетевой реализации |
| Blue-Green и Canary | Комбинация workloads и управления трафиком; не отдельные типы стратегии Deployment |

Автоматизация не появляется целиком после установки Kubernetes: нужные ресурсы, политики и интеграции должны быть настроены.

## Отличие от ручной инфраструктуры

При размещении приложения непосредственно на VM обычно отдельно настраиваются сама VM, systemd-служба, Nginx, firewall и health checks. Изменение числа экземпляров требует согласовать эти независимые настройки.

![](https://ucarecdn.stepik.net/92863ff1-ec89-4ea2-b3fb-d8860f68f7bd/)

Kubernetes предоставляет общий API и контроллеры для многих из этих действий. Описание сохраняется в Git и повторно применяется. Устройство сети, хранилища, балансировщиков и системы доступа при этом остаётся частью эксплуатации платформы.

## Kubernetes как ядро инфраструктурной платформы

| Область | Инструменты и назначение |
|---|---|
| Мониторинг | VictoriaMetrics / [[Prometheus]] и [[Grafana]]: метрики, dashboards, alerts |
| Логи | Elasticsearch/OpenSearch/Loki, Fluentd/Vector, Kibana: сбор, хранение, поиск |
| Исходный код | GitLab и другие Git-платформы |
| CI/CD | GitLab CI, Jenkins для проверок/сборки; [[ArgoCD]] для доставки по GitOps |
| Container registry | Harbor, Nexus: хранение версий образов |
| Ошибки приложения | Sentry: исключения и контекст ошибок |
| Входящий HTTP(S) | Ingress controller; статус ingress-nginx уточнён в [[Ingress]] |
| Сертификаты | cert-manager: получение и обновление TLS-сертификатов |
| Диагностика связности | [k8s-pinger](https://github.com/MadEngineX/k8s-pinger), [Goldpinger](https://github.com/bloomberg/goldpinger) |
| Аутентификация | [Dex](https://github.com/dexidp/dex), [kubelogin](https://github.com/int128/kubelogin): интеграция с OIDC |

![](https://ucarecdn.stepik.net/4874c5a0-49bd-4481-a596-9d080fbd6e6b/)

Набор компонентов зависит от требований команды. Kubernetes не заменяет сборку приложения, резервное копирование данных, централизованные логи и прикладной мониторинг.

## Ограничения и выбор

- **Эфемерность Pod.** Новый Pod может получить другой IP и оказаться на другом узле. Данные приложения требуют отдельного хранилища и восстановления. [[StatefulSet]] помогает с идентичностью и томами, но не реализует backup БД.
- **Расход ресурсов.** Control plane, системные workloads, сеть и storage потребляют CPU, RAM и место независимо от полезной нагрузки приложения.
- **Сложность сопровождения.** Необходимы знания API, Linux, сети, контейнеров и модели отказов. Ошибочная настройка может масштабировать проблему вместе с приложением.

> [!note] Критерий выбора
> Фиксированного порога «10 сервисов — Compose, 50 — Kubernetes» нет. Решение зависит от требований к доступности, масштабу, изоляции, изменениям и компетенций команды. Для небольшой системы [[Docker|Docker Compose]] может быть достаточен; Kubernetes оправдывается требованиями, а не числом сервисов само по себе.
