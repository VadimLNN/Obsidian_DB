# Управление ресурсами

[[Kubernetes|Карта тем]] · [[kubectl]] · [[Namespace, Labels и Selectors]]

Здесь **ресурс** означает API-объект Kubernetes: Pod, Deployment, Namespace и другие. Управление вычислительными ресурсами вынесено в [[Requests, Limits и QoS]].

## Объект и желаемое состояние

| Поле | Назначение |
|---|---|
| `apiVersion` | API group/version, например `v1`, `apps/v1`, `batch/v1` |
| `kind` | Тип объекта: Pod, Deployment, Job и т. д. |
| `metadata` | Имя, namespace, labels и другая идентифицирующая информация |
| `spec` | Желаемое состояние для ресурсов, у которых есть такое поле |
| `status` | Наблюдаемое состояние, обновляемое системой |

ConfigMap использует `data`, а не обязательную для всех объектов `spec`. Несколько объектов могут находиться в одном YAML-файле и разделяются `---`.

## Императивное управление

Команда задаёт конкретное изменение прямо сейчас: создание, масштабирование, редактирование или удаление ресурса.

```bash
kubectl create deployment example-deployment --image=registry.example.com/demo/example-app:v0.2
```

Здесь создаётся Deployment; обработка его контроллерами асинхронна. Команда удобна для разовой операции, но сама по себе не создаёт версионируемого описания инфраструктуры.

> [!important] Образ примеров
> `registry.example.com/demo/example-app:v0.2` — нейтральная **заглушка**, не опубликованный образ. Для запуска требуется доступный образ приложения, слушающего `0.0.0.0:8080`, совместимый с архитектурой узлов. В HTTP-примерах ожидается обработчик `/<name>` с ответом `Hi there, I love <name>!`. Это контракт демонстрационного приложения, а не функция Kubernetes. URL образа заменяется согласованно во всех запускаемых примерах; секреты registry не включаются в YAML. Подписи внутри сохранённых иллюстраций могут содержать прежние имена.

## Декларативное управление

Манифест описывает требуемое состояние. Базовый `deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-deployment
  namespace: example-app
  labels:
    app: example-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: example-app
  template:
    metadata:
      labels:
        app: example-app
    spec:
      containers:
        - name: web
          image: registry.example.com/demo/example-app:v0.2
          ports:
            - containerPort: 8080
```

Namespace `example-app` должен существовать; его манифест приведён в [[Namespace, Labels и Selectors]]. Изменение вносится в файл и применяется:

```bash
kubectl apply -f deployment.yaml
kubectl -n example-app get deployments
kubectl -n example-app get pods
```

`kubectl` обрабатывает YAML и отправляет API-запрос. Затем контроллеры создают необходимые объекты; readiness приложения проверяется отдельно.

## Infrastructure as Code и drift

Манифесты в Git позволяют проводить review, просматривать историю и воспроизводить конфигурацию. Git хранит **заявленное** состояние; фактическое состояние может отличаться из-за ручных изменений, политик и работы контроллеров.

![DevOps практики](https://ucarecdn.stepik.net/fc3daeb1-c296-456f-97a7-bff3e96d79d7/)

Например, в Git указано три реплики, а оператор временно увеличил их до четырнадцати через `kubectl edit` или `scale`. Конфигурация расходится. Последующее управление полем `replicas` из манифеста или GitOps может вернуть три реплики и снизить доступную мощность. Точный результат очередного apply зависит от способа apply и владения полями; нельзя утверждать, что любой apply обязательно перезапишет любое ручное изменение.

![](https://ucarecdn.stepik.net/563d52a5-4966-46b5-bde9-8d3e55420a4a/)

Оперативные изменения должны быть согласованы с источником желаемого состояния. Если replicas управляет HPA, ручной YAML и HPA не должны бороться за одно поле. Императивные команды полезны для диагностики и аварийных действий, но не заменяют документирование результата.

## PodTemplateSpec — композиция, а не наследование

Deployment и ReplicaSet содержат `spec.template` типа `PodTemplateSpec`. В нём находятся metadata создаваемого Pod и его `spec` типа `PodSpec`.

![](https://ucarecdn.stepik.net/2b926629-fd2c-4b53-9942-e05d863cb553/)

```bash
kubectl explain deployment.spec
kubectl explain deployment.spec.template
kubectl explain replicaset.spec.template
kubectl explain pod.spec
```

Ожидаемые типы полей:

```text
deployment.spec          → DeploymentSpec
deployment.spec.template → PodTemplateSpec
replicaset.spec.template → PodTemplateSpec
pod.spec                 → PodSpec
```

Повторяющаяся структура объясняется использованием шаблона Pod, а не наследованием API-ресурса Deployment от Pod. Внутри `template.spec` задаются контейнеры, volumes, env и probes так же, как в `spec` отдельного Pod. [[Deployment и ReplicaSet]] объясняет связи между созданными объектами.
