# Стратегии обновления

[[Kubernetes|Карта тем]] · [[Deployment и ReplicaSet]] · [[Health Checks]]

## RollingUpdate и Recreate

**RollingUpdate** постепенно меняет старые Pod на новые. Deployment увеличивает число реплик новой ReplicaSet и уменьшает старой с учётом ограничений доступности. Для Deployment это стратегия по умолчанию; явное указание полезно для читаемости конфигурации.

**Recreate** останавливает старые Pod перед созданием новых при обновлении. Она проще, но предполагает период недоступности. Это два значения `spec.strategy.type` Deployment; Canary и Blue-Green требуют дополнительных объектов и маршрутизации.

## Манифест RollingUpdate

Самостоятельный пример в namespace `example-rollout`, файл `rollout.yaml`. Образ заменяется согласно [[Управление ресурсами#Императивное управление|соглашению о примерах]].

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: example-rollout
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: example-deployment
  namespace: example-rollout
  labels:
    app: example-rollout
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  selector:
    matchLabels:
      app: example-rollout
  template:
    metadata:
      labels:
        app: example-rollout
    spec:
      containers:
        - name: web
          image: registry.example.com/demo/example-app:v0.2
          ports:
            - containerPort: 8080
```

`maxUnavailable: 1` допускает одну недоступную реплику относительно желаемых трёх. `maxSurge: 1` разрешает одну дополнительную реплику во время rollout, а не «только один новый Pod за весь процесс». Завершающиеся Pod могут временно продолжать потреблять ресурсы.

![Rolling update](https://ucarecdn.stepik.net/0a3d18ee-a9f1-4c42-a6fb-8975ac82c7e5/)

Параметры могут быть целыми числами или процентами. Для Deployment процент `maxUnavailable` округляется вниз, `maxSurge` — вверх; оба не могут быть нулевыми одновременно. [RollingUpdate Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-update-deployment).

![maxSurge maxUnavailable](https://ucarecdn.stepik.net/a28cf731-3156-4735-ad71-873023797146/)

Изменение `spec.template`, например версии образа, запускает новый rollout. Само изменение replicas не создаёт новую revision Pod template.

```bash
kubectl apply -f rollout.yaml
kubectl -n example-rollout rollout status deployment/example-deployment
kubectl -n example-rollout get replicaset
```

Для обновления в `rollout.yaml` указывается другая реально существующая версия приложения, после чего файл применяется повторно. Без смены template повторный apply не обязан создавать новые Pod.

## История, откат и restart

```bash
kubectl -n example-rollout rollout history deployment/example-deployment
kubectl -n example-rollout rollout undo deployment/example-deployment
kubectl -n example-rollout rollout restart deployment/example-deployment
```

- `history` показывает сохранённые revisions; это не [[Git]] log и не полная история данных приложения.
- `undo` возвращает предыдущий сохранённый Pod template. Старый образ и необходимая конфигурация должны оставаться доступными.
- `restart` меняет аннотацию template и инициирует пересоздание Pod согласно стратегии. Это управляемый restart, но не безусловная гарантия отсутствия простоя.

## Условия доступности

Успешный старт процесса не равен готовности принимать запросы. Без readinessProbe контроллер может считать новый Pod готовым раньше, чем готово приложение. Недостаток свободных ресурсов для `maxSurge`, неверный image или падающие probes могут остановить rollout.

Плавное обновление зависит от готовности новых Pod, корректного завершения старых соединений, совместимости версий и достаточного количества реплик. Состояние БД, содержимое volumes и внешние побочные эффекты `rollout undo` не откатывает. См. [[Requests, Limits и QoS]] и [[Диагностика и отладка]].
