## 1. Основы Git

Что такое Git?
?
Распределённая система контроля версий: каждый обычный клон содержит локальную базу объектов и историю репозитория, поэтому большинство операций выполняются локально.

Чем Git отличается от централизованной VCS?
?
В Git разработчик обычно имеет полноценный локальный репозиторий с историей, а не только рабочую копию; центральный сервер — соглашение команды, а не обязательная часть модели Git.

Какие три основные области нужно понимать в Git?
?
Working tree — файлы на диске; index/staging area — снимок, подготовленный к следующему коммиту; repository — сохранённые Git-объекты и ссылки в `.git`.

Что значит tracked file?
?
Файл известен Git: он присутствует в текущем коммите, в index или уже был добавлен в отслеживание. Tracked-файл может быть unmodified, modified или staged.

Что значит untracked file?
?
Файл существует в working tree, но Git ещё не отслеживает его и он не находится в index.

Что делает `git status`?
?
Показывает состояние working tree и index относительно текущего коммита: staged, unstaged, untracked, конфликтующие файлы и информацию о ветке.

Что делает `git init`?
?
Создаёт Git-репозиторий, обычно каталог `.git` с конфигурацией, объектной базой, refs и служебными данными; существующие файлы автоматически не коммитятся.

Что делает `git clone`?
?
Создаёт новый локальный репозиторий на основе удалённого, получает его объекты и refs, создаёт remote `origin` и обычно checkout'ит ветку по умолчанию.

Что такое snapshot в контексте Git?
?
Коммит логически фиксирует снимок дерева файлов. Неизменившийся контент переиспользуется через ссылки на уже существующие объекты, а не обязательно хранится заново как полная копия.

Что такое commit в Git?
?
Объект, который ссылается на корневой tree, родительский commit или commits, содержит автора, committer, временные метки и сообщение.

Почему commit считается неизменяемым?
?
Его идентификатор зависит от содержимого объекта. Изменение сообщения, родителя, автора или дерева создаёт новый commit с другим object ID.

Что такое commit hash / object ID?
?
Идентификатор Git-объекта, вычисляемый из его содержимого и заголовка. В современных репозиториях обычно используется SHA-1, а Git также поддерживает репозитории с SHA-256.

Можно ли считать короткий hash глобально уникальным?
?
Нет. Он лишь должен быть однозначным в конкретном репозитории на данный момент. По мере роста репозитория может понадобиться больше символов.

Что делает `git add file`?
?
Записывает текущую версию файла из working tree в index, подготавливая именно это состояние к следующему коммиту.

Почему `git add` нужно повторять после нового изменения уже staged-файла?
?
Потому что index хранит отдельный снимок. После `git add` дальнейшее изменение working tree не обновляет staged-версию автоматически.

Что делает `git commit` без дополнительных путей?
?
Создаёт новый commit из содержимого index, а не напрямую из всего working tree.

Что делает `git commit -a`?
?
Перед commit автоматически stage'ит изменения и удаления уже tracked-файлов, но не добавляет новые untracked-файлы.

Что делает `git commit --amend`?
?
Создаёт новый commit вместо текущего HEAD, используя staged-изменения и позволяя изменить сообщение; старый commit перестаёт быть вершиной ветки.

Почему опасно amend'ить уже опубликованный commit?
?
Amend переписывает commit и меняет его ID. У коллег может остаться старая версия истории, что приводит к расхождениям и необходимости согласованного force push/rebase.

Что такое `.git`?
?
Каталог с локальной базой Git: objects, refs, HEAD, index, config, reflogs, hooks и другими служебными данными.

## 2. Working tree, index и diff

Что такое staging area / index?
?
Промежуточный снимок следующего коммита. Он позволяет выбрать не все изменения working tree, а только нужные файлы или отдельные hunks.

Чем `git diff` отличается от `git diff --staged`?
?
`git diff` сравнивает working tree с index; `git diff --staged` (`--cached`) сравнивает index с HEAD.

Как посмотреть все изменения относительно HEAD, включая staged и unstaged?
?
Обычно отдельно `git diff HEAD` показывает различия working tree относительно HEAD; при этом нужно понимать, что untracked-файлы обычный diff сам по себе не показывает.

Как добавить только часть изменений файла в index?
?
Использовать `git add -p` и интерактивно выбрать hunks или их части.

Зачем нужен `git add -p` на практике?
?
Чтобы разбить смешанные изменения на логичные атомарные commits, не создавая временные копии файлов.

Что делает `git restore file`?
?
По умолчанию восстанавливает файл в working tree из index, удаляя незастейдженные изменения этого файла.

Что делает `git restore --staged file`?
?
Убирает файл из staged-состояния, восстанавливая его запись index обычно из HEAD, но сохраняет изменения в working tree.

Чем `git restore --staged` концептуально отличается от `git reset file`?
?
Для обычного unstaging результат сходен, но `restore` — более специализированная современная команда для восстановления working tree/index, тогда как `reset` также умеет перемещать ветку/HEAD.

Как отменить незастейдженные изменения конкретного tracked-файла?
?
`git restore <file>`. Это уничтожает незакоммиченные изменения working tree для этого файла, поэтому перед выполнением нужно убедиться, что они не нужны.

Что делает `git rm file`?
?
Удаляет tracked-файл из working tree и одновременно stage'ит его удаление.

Что делает `git rm --cached file`?
?
Удаляет путь из index, но оставляет файл в working tree; часто используется, чтобы перестать отслеживать файл и затем добавить его в `.gitignore`.

Что делает `git mv old new`?
?
Удобный эквивалент перемещения файла и staging соответствующего удаления/добавления. Git не хранит rename как отдельный объект, а определяет переименование эвристически при сравнении.

Хранит ли Git факт переименования файла как специальную операцию?
?
Обычно нет. Git хранит snapshots, а rename/copy обнаруживает при diff на основе сходства содержимого.

Почему добавление файла в `.gitignore` не перестаёт отслеживать уже tracked-файл?
?
`.gitignore` влияет в основном на untracked-файлы. Уже отслеживаемый путь остаётся tracked, пока его не убрать из index, например `git rm --cached`.

Для чего используется `.gitignore`?
?
Для правил игнорирования untracked-файлов и каталогов, которые не должны предлагаться к добавлению: build artifacts, локальные env-файлы, IDE-мусор и т.п.

Где кроме `.gitignore` можно задавать ignore-правила?
?
В `.git/info/exclude` для локальных правил репозитория и через глобальный excludes-файл, например настройку `core.excludesFile`.

Как принудительно добавить игнорируемый файл?
?
`git add -f <file>`, если действительно нужно добавить его несмотря на ignore-правила.

Как проверить, какое правило `.gitignore` игнорирует файл?
?
`git check-ignore -v <path>` покажет совпавший pattern и файл правил.

Что делает `git clean`?
?
Удаляет untracked-файлы из working tree. Обычно сначала используют `git clean -n`/`--dry-run`, потому что удаление может быть необратимым для данных вне Git.

Как удалить untracked-файлы и каталоги через `git clean`?
?
После проверки dry-run обычно `git clean -fd`; `-d` включает каталоги. Игнорируемые файлы без дополнительных опций не удаляются.

## 3. Ветки, HEAD и refs

Что такое branch в Git?
?
Подвижная ссылка на commit, обычно хранящаяся как ref в `refs/heads/...`. Новый commit сдвигает текущую ветку на новый commit.

Что такое HEAD?
?
Ссылка на текущую позицию checkout. Обычно HEAD символически указывает на текущую локальную ветку; в detached HEAD он указывает непосредственно на commit.

Что такое detached HEAD?
?
Состояние, когда HEAD указывает прямо на commit, а не на локальную ветку. Новые commits можно делать, но без создания ветки их легко потерять из обычных refs.

Как безопасно сохранить commits, сделанные в detached HEAD?
?
Создать ветку, указывающую на текущий commit: `git switch -c <name>` или `git branch <name>` до ухода с этой позиции.

Что делает `git branch feature`?
?
Создаёт новую локальную ветку `feature`, указывающую на текущий commit, но не переключает на неё.

Как создать ветку и сразу переключиться на неё?
?
Современно: `git switch -c feature`. Старый универсальный вариант: `git checkout -b feature`.

Чем `git switch` удобнее `git checkout` для веток?
?
`switch` специализирован на переключении/создании веток, поэтому семантика менее перегружена и ниже риск перепутать переключение ветки с восстановлением файла.

Что происходит с branch pointer после нового commit?
?
Текущая ветка автоматически перемещается на новый commit; HEAD продолжает символически указывать на эту ветку.

Как переименовать текущую ветку?
?
`git branch -m <new-name>`. Для другой локальной ветки можно указать старое и новое имя.

Как удалить локальную ветку безопасно?
?
`git branch -d <branch>` удалит её только если Git считает изменения уже слитыми в подходящую историю.

Как принудительно удалить локальную ветку?
?
`git branch -D <branch>`. Это удаляет ref даже при несмердженных commits; сами объекты некоторое время могут оставаться восстановимыми через reflog/GC.

Можно ли удалить ветку, не удалив commits немедленно?
?
Да. Ветка — лишь ref. Объекты commits остаются, пока достижимы из других refs/reflog или пока не будут со временем очищены сборкой мусора.

Что такое ref?
?
Человеко-читаемая ссылка на Git object ID: локальные ветки, remote-tracking refs, tags и другие ссылки.

Где обычно хранятся локальные ветки?
?
Логически в `refs/heads/`. Физически refs могут быть также упакованы, поэтому нельзя полагаться только на наличие отдельных файлов.

Что означает `HEAD~1`?
?
Первый родитель commit, на который указывает HEAD. `~N` N раз идёт по первому родителю.

Что означает `HEAD^`?
?
Обычно первый родитель HEAD. Для merge commit можно использовать `HEAD^1`, `HEAD^2` и т.д. для выбора конкретного родителя.

Чем `~` отличается от `^` в revision syntax?
?
`~N` повторно идёт по первому родителю; `^N` выбирает N-го непосредственного родителя конкретного commit, что особенно важно для merge commits.

Как узнать, какие ветки содержат определённый commit?
?
`git branch --contains <commit>` для локальных веток; с `-a` можно включить remote-tracking refs.

Как посмотреть граф веток в терминале?
?
Например `git log --graph --oneline --decorate --all`.

Что такое orphan branch?
?
Ветка с новой независимой корневой историей, создаваемая, например, `git switch --orphan <name>`; она не имеет обычного родительского commit от текущей истории.

## 4. Merge и конфликты

Что делает `git merge <branch>`?
?
Интегрирует историю указанной ветки в текущую: либо перемещает текущий ref fast-forward, либо создаёт merge commit, либо останавливается на конфликтах.

Что такое fast-forward merge?
?
Случай, когда текущая ветка является предком целевой. Git может просто передвинуть branch pointer вперёд без создания merge commit.

Как запретить создание merge commit, если возможен только fast-forward?
?
`git merge --ff-only <branch>` завершится ошибкой, если для интеграции нужен настоящий merge commit.

Как принудительно создать merge commit даже при возможности fast-forward?
?
`git merge --no-ff <branch>`.

Что такое three-way merge?
?
Слияние двух версий на основе их общего предка (merge base): Git сравнивает обе стороны с базой и строит объединённый результат.

Что такое merge base?
?
Лучший общий предок двух commits для целей merge. Его можно посмотреть через `git merge-base A B`.

Когда возникает merge conflict?
?
Когда Git не может однозначно объединить конкурирующие изменения, например обе стороны несовместимо меняют одну область или одна удаляет файл, который другая изменяет.

Что хранит index во время merge conflict?
?
Для конфликтующего пути index может содержать несколько stages: stage 1 — base, stage 2 — ours, stage 3 — theirs.

Что означают `ours` и `theirs` при обычном merge?
?
`ours` — версия текущей ветки, на которой выполняется merge; `theirs` — версия ветки/commit, который вливается.

Почему `ours` и `theirs` при rebase могут казаться перевёрнутыми?
?
Во время rebase commits текущей ветки переигрываются поверх новой базы; контекст merge machinery меняется, поэтому интуитивное 'моя ветка' не всегда совпадает с ours.

Как завершить merge после ручного разрешения конфликтов?
?
Исправить файлы, `git add` разрешённые пути и затем выполнить `git commit` или `git merge --continue`, если версия Git/сценарий это поддерживает.

Как отменить незавершённый merge?
?
Обычно `git merge --abort`, чтобы вернуться к состоянию до начала merge, насколько это возможно.

Что делает `git checkout --ours file` / `--theirs` в конфликте?
?
Выбирает одну из индексных сторон конфликта для файла. Современный аналог — `git restore --ours/--theirs <file>` в подходящем конфликтном состоянии.

Всегда ли отсутствие текстового конфликта означает логически корректный merge?
?
Нет. Git разрешает только структурно обнаружимые конфликты; семантические ошибки могут слиться автоматически и проявиться только в тестах или runtime.

Чем merge commit отличается от обычного commit?
?
У merge commit два или более родителя; обычный non-root commit обычно имеет одного родителя.

Что делает `git merge --squash <branch>`?
?
Готовит в index/worktree суммарный результат изменений ветки без создания merge commit и без записи связи с её историей; commit нужно создать отдельно.

Почему squash merge теряет информацию о топологии ветки?
?
Новый commit содержит итоговый diff, но не имеет второго родителя, указывающего на исходную feature-ветку.

Что такое octopus merge?
?
Merge с более чем двумя родителями, обычно для объединения нескольких независимых веток; сложные конфликтующие merges для такого режима не являются типичным применением.

Как посмотреть только merge commits?
?
`git log --merges`.

Как сравнить две ветки по изменениям относительно общего предка?
?
Часто используют `git diff A...B`: три точки для diff означают сравнение merge base(A,B) с B.

## 5. Rebase и переписывание commits

Что делает `git rebase main` из feature-ветки?
?
Находит commits feature, которых нет в новой базе, и переигрывает их поверх `main`, создавая новые commits с новыми object IDs.

Главное отличие merge от rebase?
?
Merge сохраняет существующую топологию и обычно добавляет merge commit; rebase переписывает commits, создавая линейную историю поверх другой базы.

Почему rebase меняет commit hashes?
?
Новые commits получают других родителей и часто другие метаданные, поэтому их содержимое как Git-объектов отличается.

Когда rebase опубликованной общей ветки опасен?
?
Когда другие разработчики уже строят работу на старых commits. После rewrite их история расходится, что требует координации и часто force push.

Что делает `git rebase --continue`?
?
После разрешения текущих конфликтов продолжает переигрывание оставшихся commits.

Что делает `git rebase --abort`?
?
Отменяет текущий rebase и пытается вернуть ветку в состояние до его запуска.

Что делает `git rebase --skip`?
?
Пропускает текущий commit при rebase. Это может намеренно или случайно удалить его изменения из итоговой истории.

Что такое interactive rebase?
?
`git rebase -i <base>` позволяет переупорядочивать, объединять, удалять, редактировать commits и менять их сообщения.

Что означает `pick` в interactive rebase?
?
Применить commit как есть в выбранном порядке.

Что означает `reword` в interactive rebase?
?
Оставить изменения commit, но изменить его commit message.

Что означает `edit` в interactive rebase?
?
Остановиться на commit, чтобы изменить его содержимое/метаданные, например через amend, после чего продолжить rebase.

Что означает `squash` в interactive rebase?
?
Объединить commit с предыдущим и позволить отредактировать итоговое сообщение.

Что означает `fixup` в interactive rebase?
?
Объединить commit с предыдущим, обычно отбросив его отдельное сообщение; существуют дополнительные варианты поведения fixup в новых Git.

Как объединить последние несколько локальных commits в один?
?
Обычно `git rebase -i HEAD~N`, оставив первый `pick`, а последующие пометив `squash`/`fixup`.

Как изменить сообщение не последнего локального commit?
?
Использовать interactive rebase до его родителя и выбрать `reword`; это перепишет этот и все последующие commits в цепочке.

Как удалить commit из локальной истории через interactive rebase?
?
Удалить соответствующую строку или использовать `drop`; изменения этого commit исчезнут, если не присутствуют в других commits.

Что делает `git rebase --onto newbase upstream branch`?
?
Берёт commits `branch`, которые находятся после `upstream`, и переигрывает их поверх `newbase`; полезно для переноса части цепочки commits.

Что означает autosquash?
?
`git rebase -i --autosquash` автоматически размещает commits с сообщениями `fixup!`/`squash!` рядом с целевыми и выставляет соответствующие действия.

Для чего `git commit --fixup <commit>`?
?
Создаёт commit, предназначенный для последующего автоматического объединения с указанным commit через autosquash.

Чем rebase отличается от cherry-pick?
?
Оба переигрывают изменения commits, но rebase системно переносит последовательность commits на новую базу, а cherry-pick обычно явно выбирает отдельные commits.

Может ли rebase изменить только topology, сохранив итоговое содержимое файлов?
?
Да. Часто итоговое дерево файлов остаётся тем же, но commits и их родительские связи становятся новыми.

Что делает `git pull --rebase`?
?
Сначала fetch, затем вместо merge переигрывает локальные commits текущей ветки поверх обновлённой upstream-ветки.

## 6. Reset, revert, restore и восстановление

Что делает `git reset` концептуально?
?
Перемещает текущую ветку/HEAD к указанному commit и, в зависимости от режима, также изменяет index и working tree.

Что делает `git reset --soft <commit>`?
?
Перемещает HEAD/ветку, но оставляет index и working tree как были. Изменения относительно нового HEAD остаются staged.

Что делает `git reset --mixed <commit>`?
?
Это типичный режим по умолчанию: перемещает HEAD и сбрасывает index к целевому commit, но сохраняет изменения в working tree как unstaged.

Что делает `git reset --hard <commit>`?
?
Перемещает HEAD, сбрасывает index и tracked-файлы working tree к указанному commit, уничтожая соответствующие незакоммиченные изменения.

Удаляет ли `git reset --hard` все untracked-файлы?
?
Нет. Для удаления untracked обычно нужен `git clean`; однако файлы могут быть затронуты, если мешают checkout/reset tracked-путей в конкретных случаях.

Чем `git revert` отличается от `git reset`?
?
`revert` создаёт новый commit, который отменяет изменения старого, поэтому подходит для опубликованной истории. `reset` перемещает refs и может переписывать локальную историю.

Как отменить уже запушенный обычный commit в общей ветке?
?
Обычно безопаснее `git revert <commit>` и push нового отменяющего commit, а не переписывать общую историю reset'ом.

Что делает `git revert <commit>`?
?
Вычисляет обратные изменения указанного commit и создаёт новый commit с этой инверсией, если не возникнут конфликты.

Почему revert merge commit требует выбора mainline?
?
У merge несколько родителей, поэтому Git нужно указать, относительно какого родителя считать изменения merge: `git revert -m <parent-number> <merge>`.

Что такое reflog?
?
Локальный журнал изменений значений refs/HEAD: checkout, commit, reset, rebase и другие перемещения. Он помогает найти commits, потерянные из обычной истории.

Я случайно сделал `git reset --hard HEAD~3`. Как искать прежний HEAD?
?
Сначала `git reflog`, найти запись до reset и затем создать ветку или reset'нуться на нужный object ID.

Почему reflog нельзя считать удалённым резервным копированием?
?
Он локален для конкретного репозитория, имеет сроки хранения и со временем записи/недостижимые объекты могут быть очищены.

Как восстановить случайно удалённую локальную ветку?
?
Найти её прежний tip через `git reflog`/reflog HEAD и создать новую ветку: `git branch <name> <commit>`.

Что такое `ORIG_HEAD`?
?
Служебный ref, который некоторые опасные операции записывают перед перемещением HEAD, чтобы было проще вернуться к предыдущей позиции; нельзя полагаться, что он подходит для любой ситуации.

Как отменить последний локальный commit, сохранив его изменения staged?
?
`git reset --soft HEAD~1`.

Как отменить последний локальный commit, сохранив изменения unstaged?
?
`git reset HEAD~1` или явно `git reset --mixed HEAD~1`.

Как полностью отбросить последний локальный commit вместе с tracked-изменениями?
?
`git reset --hard HEAD~1`, если точно известно, что данные не нужны.

Как убрать конкретный файл из последнего commit, если commit ещё не опубликован?
?
Восстановить нужное состояние index, например `git restore --staged <file>`, затем `git commit --amend`; конкретная последовательность зависит от того, нужно ли сохранить изменения файла в working tree.

Как восстановить удалённый tracked-файл до версии из HEAD?
?
`git restore <file>`, если удаление ещё не закоммичено.

Как получить версию файла из другого commit, не переключая всю ветку?
?
`git restore --source=<commit> -- <path>`; старый вариант — `git checkout <commit> -- <path>`.

Что делает `git fsck --lost-found`?
?
Проверяет связность/валидность object database и может помочь найти dangling/unreachable objects; это низкоуровневый вариант восстановления, когда reflog недостаточен.

Что значит dangling commit?
?
Commit-объект, который существует в object database, но больше не достижим через обычные refs; пока объект не удалён GC, его иногда можно восстановить.

Что делает `git reflog expire`?
?
Управляет истечением reflog-записей. Агрессивное истечение вместе с GC может существенно уменьшить возможности восстановления.

Когда `reset --hard` безопаснее всего?
?
На локальных изменениях/ветках, состояние которых точно не нужно другим и для которых потеря незакоммиченных данных приемлема; перед выполнением полезно проверить status/reflog или сделать backup branch.

## 7. Remotes, fetch, pull и push

Что такое remote в Git?
?
Именованная конфигурация URL и refspec'ов удалённого репозитория. `origin` — только распространённое имя, не специальный сервер Git.

Что такое `origin`?
?
Обычное имя remote, которое `git clone` обычно создаёт автоматически для источника клонирования; его можно переименовать или удалить.

Что делает `git remote -v`?
?
Показывает remotes и настроенные URL для fetch/push.

Что делает `git fetch`?
?
Получает объекты и обновляет remote-tracking refs согласно refspec, не выполняя автоматически merge/rebase в текущую локальную ветку.

Что такое remote-tracking branch, например `origin/main`?
?
Локально хранимая ref, отражающая последнее известное Git состояние соответствующей ветки remote после fetch/push; это не сама серверная ветка.

Чем `main` отличается от `origin/main`?
?
`main` — локальная ветка, которую ты двигаешь commits; `origin/main` — локальная remote-tracking ref, обновляемая взаимодействием с `origin`.

Что делает `git pull`?
?
По сути выполняет fetch и затем интеграцию upstream в текущую ветку, обычно merge или rebase в зависимости от параметров/конфигурации.

Почему многие предпочитают `fetch` + явный `merge/rebase` вместо `pull`?
?
Так видно, что именно пришло с remote, и решение об интеграции принимается отдельно, что уменьшает неожиданные merge/rebase действия.

Что делает `git push origin feature`?
?
Отправляет необходимые объекты и просит remote обновить соответствующую ветку `feature` согласно refspec, если сервер разрешает обновление.

Что означает `git push -u origin feature`?
?
Push'ит ветку и настраивает upstream/tracking связь, чтобы последующие `git push`/`git pull` могли использовать её по умолчанию.

Что такое upstream branch?
?
Ветка, с которой локальная ветка настроена сравниваться и обычно синхронизироваться для pull/push; часто это `origin/<name>`.

Как посмотреть upstream текущей ветки?
?
Например `git branch -vv` или `git rev-parse --abbrev-ref --symbolic-full-name @{u}`.

Что значит ahead/behind относительно upstream?
?
Ahead — локальные commits, которых нет в upstream; behind — commits upstream, которых нет в локальной ветке.

Почему обычный push может быть rejected как non-fast-forward?
?
Remote ref уже содержит commits, которых нет в истории отправляемого tip. Обновление потеряло бы достижимость чужих commits, поэтому Git/сервер обычно запрещает его без force.

Что делает `git push --force`?
?
Просит remote обновить ref даже не-fast-forward способом, потенциально удаляя из общей видимой истории commits других разработчиков.

Почему `--force-with-lease` безопаснее `--force`?
?
Он force-push'ит только если удалённая ref находится в ожидаемом состоянии; если кто-то обновил ветку после твоего последнего знания, операция обычно отклонится.

Абсолютно ли `--force-with-lease` защищает от потери чужой работы?
?
Нет. Его безопасность зависит от корректности ожидаемой remote-tracking информации и workflow; автоматический fetch и явные формы lease могут влиять на гарантии.

Как удалить ветку на remote?
?
`git push <remote> --delete <branch>`.

Что делает `git fetch --prune`?
?
После fetch удаляет устаревшие remote-tracking refs, для которых соответствующие refs уже удалены на remote, согласно настройкам.

Что делает `git remote prune origin`?
?
Удаляет устаревшие remote-tracking refs для `origin` без обычного получения новых объектов как основного действия.

Что такое refspec?
?
Правило сопоставления refs между локальным и удалённым репозиторием, например какие remote branches получать и в какие `refs/remotes/...` их записывать.

Что значит `+` в refspec?
?
Разрешает non-fast-forward обновление соответствующей ref при fetch/push refspec; использовать нужно осознанно.

Как добавить второй remote, например upstream?
?
`git remote add upstream <url>`. Такое имя часто используют для оригинального репозитория при работе через fork.

Типичный workflow с fork и `upstream`?
?
`origin` указывает на собственный fork, `upstream` — на основной проект; обновления получают через `git fetch upstream`, затем интегрируют в локальные ветки и push'ят в origin.

Чем fetch URL может отличаться от push URL?
?
Git позволяет настроить разные адреса для получения и отправки, например читать по HTTPS, а push делать по SSH.

Что делает `git ls-remote <url>`?
?
Показывает refs и object IDs удалённого репозитория без полноценного clone.

Что такое shallow clone?
?
Клон с ограниченной глубиной истории, например `git clone --depth 1`; часть commits/ancestry отсутствует локально, пока историю не углубить.

Какие ограничения бывают у shallow clone?
?
Операции, требующие полной ancestry/history, могут работать ограниченно; при необходимости используют `git fetch --deepen`, `--unshallow` и т.п.

## 8. Cherry-pick, stash и tags

Что делает `git cherry-pick <commit>`?
?
Применяет изменения выбранного commit поверх текущего HEAD и обычно создаёт новый commit с новым object ID.

Когда cherry-pick полезнее merge?
?
Когда нужно перенести один или несколько конкретных исправлений без интеграции всей ветки, например backport bugfix.

Как cherry-pick диапазон commits?
?
Можно указывать несколько commits или диапазоны revision syntax; важно понимать включённость границ, например `A^..B` включает A и B при линейной цепочке.

Как отменить конфликтующий незавершённый cherry-pick?
?
`git cherry-pick --abort`.

Что делает `git cherry-pick --no-commit`?
?
Применяет изменения выбранных commits в index/working tree без автоматического создания commit, чтобы объединить/отредактировать результат.

Что делает `git stash`?
?
Сохраняет изменения рабочего состояния во внутренние Git-объекты/refs и обычно возвращает working tree к более чистому состоянию; точный набор зависит от опций.

Сохраняет ли обычный `git stash` untracked-файлы?
?
По умолчанию нет; для них используют `git stash -u`/`--include-untracked`. Игнорируемые файлы требуют `-a`/`--all`.

Чем `git stash apply` отличается от `git stash pop`?
?
`apply` применяет stash и оставляет запись в списке; `pop` применяет и при успешном применении пытается удалить запись stash.

Что делает `git stash list`?
?
Показывает стек stash-записей, например `stash@{0}`, `stash@{1}`.

Как применить не последний stash?
?
`git stash apply stash@{N}` или `git stash pop stash@{N}`.

Что делает `git stash branch <name> [stash]`?
?
Создаёт ветку от commit, на котором stash был сделан, checkout'ит её и применяет stash; полезно при конфликтах на сильно изменившейся текущей ветке.

Что такое tag в Git?
?
Ref, обычно используемая для именования конкретного состояния, например релиза. Бывают lightweight и annotated tags.

Чем annotated tag отличается от lightweight tag?
?
Annotated tag создаёт отдельный tag object с автором tagger, датой, сообщением и возможной подписью; lightweight tag — по сути простая ref на object.

Как создать annotated tag?
?
`git tag -a v1.2.0 -m '...'`.

Отправляются ли tags обычным `git push` автоматически?
?
Обычно нет все подряд. Можно push'нуть конкретный tag или использовать `git push --tags`; также существует `--follow-tags` для подходящих annotated tags.

Как удалить tag локально и на remote?
?
Локально `git tag -d <tag>`; на remote `git push <remote> --delete <tag>` или эквивалентный refspec.

## 9. Просмотр, поиск и диагностика

Что делает `git log`?
?
Показывает историю commits, достижимых из выбранных revision, с множеством фильтров и форматов.

Что полезного показывает `git log --oneline --decorate --graph --all`?
?
Компактный граф достижимой истории с названиями refs для всех локально известных веток/refs.

Что делает `git show <commit>`?
?
Показывает объект/commit и обычно patch относительно родителя, плюс метаданные.

Чем `git diff A B` отличается от `git diff A..B`?
?
Для `git diff` две точки обычно не дают особой семантики диапазона: оба варианта сравнивают snapshots A и B. Это отличается от range syntax в `git log`.

Что означает `A..B` в `git log`?
?
Commits, достижимые из B, но не достижимые из A.

Что означает `A...B` в `git log`?
?
Симметрическая разность: commits, достижимые только с одной стороны, но не с обеих.

Что означает `A...B` в `git diff`?
?
Сравнение merge base(A,B) с B; это не то же самое, что three-dot range в `git log`.

Как посмотреть, кто и в каком commit последним изменил каждую строку файла?
?
`git blame <file>`. Результат нужно интерпретировать осторожно: форматирование и перемещения могут скрывать первоначальный источник строки.

Как найти commits, где количество вхождений строки изменилось?
?
`git log -S'<text>'` — pickaxe search по изменению количества указанной строки.

Чем `git log -G<regex>` отличается от `-S<string>`?
?
`-G` ищет commits, где diff содержит строки, соответствующие regex; `-S` ищет изменение количества вхождений конкретной строки.

Что делает `git grep`?
?
Ищет текст/regex по tracked-содержимому Git, обычно быстрее и удобнее для репозитория, чем общий файловый grep в некоторых сценариях.

Для чего нужен `git bisect`?
?
Для бинарного поиска первого плохого commit между известными good и bad точками.

Каков базовый workflow `git bisect`?
?
`git bisect start`, отметить bad и good commits, тестировать предлагаемые Git commits и отмечать `good`/`bad`, затем `git bisect reset`.

Что делает `git bisect run <command>`?
?
Автоматизирует bisect, запуская команду/скрипт на каждом кандидате и классифицируя commit по exit code.

Что делает `git rev-parse`?
?
Разбирает revision/параметры и может выдавать object IDs или служебную информацию; часто используется в скриптах.

Как проверить, является ли commit A предком B?
?
`git merge-base --is-ancestor A B`; exit code сообщает результат.

Что делает `git describe`?
?
Строит читаемое имя commit на основе ближайшего подходящего tag и количества commits/сокращённого hash, в зависимости от опций.

Как посмотреть изменения одного файла по истории, включая попытки отслеживать rename?
?
Например `git log --follow -- <file>`; `--follow` имеет ограничения и работает для одного пути.

## 10. Внутренности Git

Какие основные типы объектов Git нужно знать?
?
blob, tree, commit и annotated tag object.

Что хранит blob object?
?
Содержимое файла как последовательность байтов. Имя файла и путь в blob не хранятся.

Что хранит tree object?
?
Список записей с mode, именем и ссылкой на blob/tree или gitlink; таким образом tree представляет каталог/снимок структуры.

Что хранит commit object?
?
Ссылку на корневой tree, parent/parents, author, committer, временные данные и commit message.

Как Git связывает имя файла с blob?
?
Имя хранится в записи tree object, которая указывает на object ID blob или поддерева.

Почему два одинаковых файла могут использовать один blob object?
?
Object ID зависит от содержимого объекта; одинаковое содержимое даёт один и тот же объект в рамках выбранного object format, поэтому Git может переиспользовать его.

Что такое content-addressable storage в Git?
?
Объект адресуется идентификатором, вычисленным из его собственного содержимого, а не произвольным номером записи.

Что находится в `.git/objects`?
?
Object database: loose objects и служебные каталоги для packfiles/info. Большие наборы объектов обычно упаковываются.

Что такое packfile?
?
Компактный формат хранения множества Git-объектов с компрессией и delta-compression для экономии места и эффективной передачи.

Что делает `git gc`?
?
Выполняет обслуживание репозитория: упаковку объектов, очистку некоторых недостижимых данных по правилам/срокам и другие оптимизации.

Что делает `git cat-file -p <object>`?
?
Показывает содержимое Git-объекта в удобном виде, позволяя исследовать blobs, trees, commits и tags.

Что делает `git hash-object`?
?
Вычисляет object ID для содержимого; с соответствующими опциями может записать blob в object database.

Что делает `git write-tree`?
?
Создаёт tree object из текущего состояния index и возвращает его object ID.

Что такое plumbing и porcelain команды?
?
Porcelain — высокоуровневый пользовательский интерфейс вроде `status`, `commit`, `switch`; plumbing — низкоуровневые строительные блоки вроде `cat-file`, `hash-object`, `update-index`.

Что хранится в `.git/index`?
?
Бинарное представление staging area: пути, object IDs, file modes и дополнительная служебная информация; во время конфликтов возможны несколько stages одного пути.

Что находится в `.git/HEAD`?
?
Обычно symbolic ref вроде `ref: refs/heads/main`; в detached HEAD — непосредственно object ID commit.

Может ли branch ref указывать не на commit?
?
Обычные refs в `refs/heads/` должны указывать на commit; tags могут ссылаться на разные типы объектов, хотя чаще тегируют commits.

Что такое symbolic ref?
?
Ref, которая хранит имя другой ref вместо object ID; главный пример — HEAD, указывающий на текущую ветку.

Что такое reachability в Git?
?
Объект достижим, если до него можно дойти от refs/reflogs и других корней по ссылкам объектов. Недостижимые объекты со временем могут быть удалены.

Почему Git может восстановить недавно 'удалённый' commit?
?
Удаление ветки/reset обычно сначала убирает ссылку, а сам object ещё существует в object database и часто упоминается reflog до истечения/GC.

## 11. Config, hooks, worktree, submodules и продвинутые возможности

Какие уровни конфигурации Git наиболее типичны?
?
System, global и local/repository; более специфичная настройка обычно переопределяет менее специфичную. Также есть worktree-specific и command-scope механизмы.

Как посмотреть все настройки Git вместе с источником?
?
`git config --list --show-origin`; при необходимости можно добавить `--show-scope`.

Где хранится локальная конфигурация репозитория?
?
Обычно в `.git/config`, если не используются особые layout/worktree механизмы.

Что делает `core.autocrlf`?
?
Управляет преобразованием окончаний строк между working tree и repository в определённых workflow; настройку нужно выбирать согласованно с `.gitattributes`, чтобы избежать шумных diff.

Почему `.gitattributes` часто лучше для правил line endings, чем личный global config?
?
Она версионируется вместе с репозиторием и задаёт единые правила для команды независимо от локальной машины.

Для чего используется `.gitattributes`?
?
Для attributes путей: text/eol normalization, diff/merge drivers, linguist-like external consumers, export-ignore и других Git-механизмов.

Что такое Git hook?
?
Скрипт, запускаемый Git на определённых событиях, например pre-commit, commit-msg, pre-push или server-side receive hooks.

Почему нельзя полагаться только на client-side hooks для обязательной политики?
?
Пользователь может не установить hook, изменить его или обойти. Критические проверки должны дублироваться CI/server-side controls.

Что такое `git worktree`?
?
Механизм нескольких рабочих деревьев, связанных с одной repository object database, позволяющий одновременно checkout'ить разные ветки без отдельных полных clones.

Как создать дополнительный worktree для ветки?
?
Например `git worktree add ../project-hotfix hotfix`; Git создаст связанную рабочую директорию.

Почему одна и та же branch обычно не может быть checkout'нута в двух worktrees одновременно?
?
Git защищает от одновременного независимого изменения одного branch ref из нескольких рабочих деревьев.

Что такое submodule?
?
Запись в основном репозитории, которая фиксирует конкретный commit другого Git-репозитория; working tree submodule живёт как отдельный репозиторий.

Что хранит superproject для submodule?
?
Gitlink с object ID конкретного commit submodule плюс конфигурационные данные/URL обычно в `.gitmodules`.

Почему после `git pull` submodule может не оказаться на последнем commit своей remote-ветки?
?
Superproject фиксирует конкретный commit submodule, а не автоматически 'последнюю версию'. Его нужно обновлять согласно submodule workflow.

Как клонировать репозиторий вместе с submodules?
?
`git clone --recurse-submodules <url>` либо после clone выполнить `git submodule update --init --recursive`.

Что такое sparse checkout?
?
Режим, при котором working tree содержит только выбранное подмножество tracked-путей, хотя repository знает больше файлов.

Для чего sparse checkout полезен?
?
Для больших monorepo, когда разработчику нужна только часть дерева и хочется уменьшить рабочий набор/ускорить некоторые операции.

Что такое partial clone?
?
Clone, который может не загружать часть объектов сразу, используя promisor remote и фильтры; недостающие объекты получают по требованию.

Чем partial clone отличается от shallow clone?
?
Shallow ограничивает историю commits; partial clone может сохранять граф истории, но откладывать загрузку определённых объектов, например blobs.

Что делает `git rerere`?
?
Reuse Recorded Resolution: запоминает способ разрешения конфликтов и может автоматически переиспользовать его при повторении похожего конфликта.

Когда `rerere` особенно полезен?
?
При длительных rebases, повторных merges и поддержке веток, где одни и те же конфликты возникают снова.

Что такое commit signing?
?
Криптографическая подпись commit/tag, позволяющая проверять, что объект подписан владельцем соответствующего ключа; Git поддерживает несколько signing formats в зависимости от конфигурации.

Что делает `git verify-commit`?
?
Проверяет криптографическую подпись указанного commit, если она есть и формат/ключи доступны.

Что делает `git archive`?
?
Создаёт архив содержимого выбранного tree-ish без каталога `.git`, обычно для поставки snapshot исходников.

Что такое Git bundle?
?
Один файл, содержащий Git-объекты и refs, пригодный для офлайн-переноса части/всего репозитория через `git bundle`.

Для чего нужен `git maintenance`?
?
Для запуска и планирования задач обслуживания репозитория, особенно полезных для больших репозиториев.

## 12. Практические сценарии собеседований

Ты сделал commit, но забыл добавить один файл. Commit ещё не push'ил. Что делать?
?
`git add <file>` затем `git commit --amend --no-edit`, если файл действительно должен быть частью того же атомарного commit.

Ты ошибся в сообщении последнего локального commit. Что делать?
?
`git commit --amend` и изменить message. Если commit уже опубликован, сначала оценить последствия rewrite.

Ты начал feature от неправильной базы, но commits ещё локальные. Как перенести их на актуальный `main`?
?
Fetch/update базы и rebase feature на нужную базу, например `git rebase main`; для сложного переноса части цепочки — `rebase --onto`.

У тебя незаконченные изменения, а нужно срочно переключиться на hotfix. Какие варианты?
?
Сделать временный WIP commit в отдельной ветке или использовать `git stash` (при необходимости `-u`), затем переключиться на hotfix.

Ты случайно сделал commit в `main`, но ещё не push'ил. Commit должен быть в новой feature-ветке. Что делать?
?
Создать ветку на текущем commit, затем вернуть `main` к прежней точке: например `git switch -c feature`, потом `git switch main` и `git reset --hard HEAD~1` после проверки.

Ты случайно сделал несколько commits в `main`, они не опубликованы, и хочешь перенести их в feature. Что делать?
?
Создать feature на текущем tip, затем reset'нуть локальный main на нужный исходный commit/upstream; перед hard reset убедиться, что feature действительно сохранила commits.

Ты удалил локальную ветку с незамерженными commits. Что делать?
?
Найти tip через `git reflog`/reflog HEAD и создать новую branch на найденном commit.

После `git reset --hard` пропала работа. Первый инструмент диагностики?
?
`git reflog` — если работа была хотя бы commit'нута или ref/HEAD на неё указывал. Чисто незакоммиченные изменения Git может не иметь возможности восстановить.

Ты изменил файл после `git add`, а затем сделал commit. Какая версия попадёт в commit?
?
Версия, находившаяся в index на момент commit; более новые unstaged-изменения working tree останутся вне commit.

В `git status` один и тот же файл одновременно staged и modified. Что это значит?
?
В index лежит одна версия файла, а после staging working tree был изменён ещё раз; commit возьмёт staged-версию.

Ты добавил `.env` в `.gitignore`, но `git status` продолжает показывать его изменения. Почему?
?
Файл уже tracked. Нужно убрать его из index (`git rm --cached .env`) и отдельно решить вопрос с уже опубликованными секретами.

Секрет попал в commit и был push'нут. Достаточно ли удалить файл новым commit?
?
Нет. Секрет остаётся в доступной истории и его нужно считать скомпрометированным: немедленно revoke/rotate credential, затем при необходимости очищать историю специализированным rewrite-инструментом и координировать force update.

Почему при утечке API key первым действием должна быть ротация, а не переписывание Git history?
?
Потому что секрет уже мог быть скопирован, закеширован, попасть в forks/logs. Удаление из истории не делает старый credential снова безопасным.

Коллега push'нул новые commits, а ты переписал свою feature через rebase. Как push'ить безопаснее?
?
После fetch и проверки использовать `git push --force-with-lease`, если командный workflow разрешает rewrite этой feature-ветки.

Почему нельзя бездумно `git push --force` в общую `main`?
?
Можно перезаписать tip remote и сделать чужие commits недостижимыми из ветки, ломая историю и работу коллег.

Нужно забрать один bugfix commit из другой ветки без merge всей ветки. Что использовать?
?
`git cherry-pick <commit>`, затем разрешить возможные конфликты и проверить результат.

Нужно отменить ошибочный commit, который уже в общей `main`. Что предпочесть?
?
`git revert <commit>`, потому что он добавит компенсирующий commit без переписывания опубликованных refs.

Нужно убрать последний локальный commit, но оставить изменения для доработки. Какая команда?
?
`git reset --mixed HEAD~1` оставит изменения в working tree unstaged; `--soft` оставит их staged.

Нужно посмотреть изменения с remote перед интеграцией. Что делать?
?
`git fetch`, затем изучить `git log`, `git diff` и граф между своей веткой и `origin/...`, после чего явно merge/rebase.

После fetch `origin/main` обновился, а локальный `main` нет. Это ошибка?
?
Нет. Fetch обновляет remote-tracking refs, но не обязан перемещать локальную branch `main`.

Локальная ветка говорит `[gone]` в `git branch -vv`. Что это значит?
?
Её настроенный upstream ref больше не существует локально, часто потому что remote branch удалена и refs были pruned/fetched.

Как проверить, какие commits есть в feature, но нет в main?
?
`git log main..feature`; для содержательных различий также применяют diff, но range semantics у log и diff различаются.

Как увидеть commits, уникальные для обеих расходящихся веток?
?
`git log --left-right A...B` удобно показывает симметрическую разность с указанием стороны.

Feature сильно отстала от main. Когда выбрать merge main в feature, а когда rebase?
?
Merge сохраняет существующую историю и безопаснее для уже общей ветки; rebase делает линейную историю, но переписывает feature commits. Выбор зависит от командной политики и опубликованности commits.

После rebase возник один и тот же конфликт на нескольких commits. Что может помочь?
?
`git rerere` может запомнить и повторно применить ранее сделанное разрешение; также можно пересмотреть структуру commits/базу.

Ты хочешь проверить старый commit, не двигая существующие ветки. Что делать?
?
Можно `git switch --detach <commit>` или создать отдельный worktree, если параллельно нужно сохранить текущую рабочую директорию.

Ты сделал commits в detached HEAD и переключился назад. Они потеряны навсегда?
?
Не обязательно. Найти tip обычно можно через `git reflog`, пока записи/объекты не очищены, и создать на нём ветку.

Ветка не удаляется через `git branch -d`. Почему?
?
Git считает, что ветка содержит commits, которые не слиты в релевантную историю. Нужно проверить их и либо merge/rebase/cherry-pick, либо осознанно использовать `-D`.

После merge тесты сломались, хотя конфликтов не было. Как это объяснить на собеседовании?
?
Git обнаруживает текстовые/структурные конфликты, но не понимает бизнес-логику. Автоматически слитые изменения могут быть семантически несовместимы.

Нужно найти commit, который внёс regression, и есть автоматический тест. Лучший Git-инструмент?
?
`git bisect run <test-command>` при наличии known-good и known-bad точек.

Нужно понять, в каком commit исчез конкретный вызов функции. Какие инструменты?
?
`git log -S'functionName'`, при необходимости `-G<regex>`, `git blame` и просмотр patches через `git show`.

Почему `git blame` не доказывает, кто первоначально написал строку?
?
Он показывает commit, которому текущая строка атрибутируется после преобразований; refactor, перемещения, форматирование и опции similarity могут изменить attribution.

Две ветки имеют одинаковое содержимое файлов, но разные hashes commits. Возможно ли это?
?
Да. Commit ID зависит не только от tree, но и от родителей, автора/committer metadata и сообщения; одинаковый snapshot может находиться в разных commits.

Почему cherry-pick того же изменения может создать новый hash?
?
Новый commit обычно имеет другого родителя и возможно другие метаданные, поэтому object ID другой, даже если patch логически тот же.

Почему после squash merge Git иногда не считает исходные feature commits слитыми по ancestry?
?
Squash создаёт новый commit с итоговым diff, но без родительской связи с commits feature; топологическая ancestry не содержит их как предков.

Можно ли определить, что две ветки имеют одинаковый итоговый snapshot?
?
Да, можно сравнить trees/diff их tips; отсутствие diff означает одинаковое содержимое snapshot, хотя история commits может различаться.

Что произойдёт с untracked-файлом при `git reset --hard`?
?
Обычно он останется. Для удаления untracked используют `git clean`, но конфликт пути с tracked-файлом при операции может быть отдельным случаем.

Почему `git checkout .` или `git restore .` опасны?
?
Они могут массово уничтожить незастейдженные изменения tracked-файлов в working tree.

У тебя есть staged и unstaged изменения одного файла. Как увидеть каждую часть отдельно?
?
`git diff --staged` показывает staged относительно HEAD, а `git diff` — unstaged относительно index.

Как сделать атомарный commit, если в файле смешаны две задачи?
?
Использовать `git add -p`/interactive staging, выбрать hunks одной задачи, проверить `git diff --staged`, commit, затем подготовить оставшееся.

Почему маленькие атомарные commits полезны кроме красоты истории?
?
Их проще review'ить, revert'ить, cherry-pick'ить, bisect'ить и понимать причинность изменений.

Когда WIP commit может быть лучше stash?
?
Когда работу важно явно привязать к branch/history, синхронизировать или не потерять; перед merge можно позже squash/fixup по политике команды.

Можно ли stash использовать как долговременное хранилище работы?
?
Технически можно некоторое время, но это слабый workflow: stash менее заметен и локален. Для долгой работы надёжнее отдельная branch с commits.

Нужно одновременно держать `main` и `release` открытыми в разных каталогах. Что использовать?
?
`git worktree`, чтобы не делать два полных клона одной object database.

В monorepo нужен только каталог `backend/`. Какие Git-механизмы могут помочь?
?
Sparse checkout уменьшит набор файлов working tree; partial clone может дополнительно уменьшить первоначальную загрузку объектов.

После clone с submodules директории submodule пустые или не checkout'нуты. Что делать?
?
`git submodule update --init --recursive` или изначально clone с `--recurse-submodules`.

Почему изменение файлов внутри submodule не является обычным изменением файлов superproject?
?
Submodule — отдельный Git-репозиторий. Superproject отслеживает только gitlink на конкретный commit submodule, а не его внутренние файлы.

Ты обновил submodule до нового commit. Что нужно закоммитить в superproject?
?
Изменение gitlink — новый object ID submodule; при изменении конфигурации также `.gitmodules`.

На CI нужен воспроизводимый исходный код submodule. Почему нельзя просто брать latest main submodule?
?
Superproject должен фиксировать конкретный commit, иначе сборка зависит от изменяемого внешнего состояния и перестаёт быть воспроизводимой.

Как объяснить разницу между Git и GitHub на собеседовании?
?
Git — система контроля версий и набор локальных/сетевых механизмов; GitHub — хостинг и платформа вокруг Git с PR, issues, CI-интеграциями, permissions и т.д.

Что лучше ответить на вопрос 'какая Git-команда самая опасная'?
?
Опасность зависит от контекста. Типичные кандидаты — `reset --hard`, `clean -fdx`, force push и history rewrite, потому что они могут уничтожить незакоммиченные данные или переписать общие refs.

Какой общий принцип помогает безопасно работать с Git-командами, переписывающими историю?
?
Сначала определить, опубликованы ли commits и есть ли на них чужая работа; сохранить backup ref/reflog, проверить status/diff и только затем переписывать/force-push'ить.

Как диагностировать ситуацию 'мой commit пропал после rebase'?
?
Проверить новый `git log`, затем `git reflog` для старых tips; commit мог быть переписан, признан пустым/дубликатом или пропущен после конфликта.

Почему commit во время rebase может стать empty?
?
Его изменения уже присутствуют в новой базе или были полностью поглощены разрешением предыдущих commits; Git может предложить drop/skip или специальное сохранение empty commit.

Что делать перед сложным rebase, если боишься потерять работу?
?
Убедиться в чистом status и создать временную backup branch/tag на текущем tip; тогда возврат не зависит только от reflog.

Почему `git pull` в рабочей ветке может неожиданно создать merge commit?
?
Если pull настроен на merge и локальная/remote истории разошлись, после fetch Git выполняет merge вместо fast-forward.

Как запретить `git pull` создавать merge commit и принимать только fast-forward?
?
Настроить/использовать fast-forward-only, например `git pull --ff-only` или соответствующую конфигурацию.

Как сделать pull с линейной локальной историей?
?
Использовать `git pull --rebase` или настроить `pull.rebase`, понимая, что локальные commits будут переписаны.

Почему нельзя механически использовать rebase для `main`, если команда работает через merge commits?
?
Можно разрушить принятую топологию, переписать опубликованные commits и усложнить синхронизацию. Стратегия должна соответствовать workflow репозитория.

Что проверить перед удалением remote branch после merge PR?
?
Убедиться, что нужные commits/изменения интегрированы, локальная работа не зависит от ветки, и понимать, что удаление remote ref не удаляет автоматически локальные ветки.

Почему после удаления remote branch `origin/feature` может ещё отображаться?
?
Локальная remote-tracking ref остаётся до fetch с prune или явного pruning.

Как объяснить конфликт delete/modify?
?
Одна сторона удалила файл относительно merge base, другая изменила его. Git не знает, нужно ли сохранить изменённый файл или принять удаление.

Что такое rename/rename conflict?
?
Обе стороны переименовали один исходный путь по-разному или rename взаимодействует с другими изменениями так, что Git не может однозначно выбрать итоговую структуру.

Почему rebase может конфликтовать на каждом commit, хотя финальный merge конфликтовал бы один раз?
?
Rebase переигрывает commits по одному, поэтому каждый промежуточный patch должен примениться к новой базе; merge объединяет tips одним трехсторонним merge.

Когда squash перед merge полезен, а когда вреден?
?
Полезен для очистки множества WIP commits; вреден, если отдельные commits несут ценную причинность, облегчают revert/bisect или нужны для review/audit.

Нужно сделать release tag на конкретном commit, не текущем HEAD. Можно?
?
Да: `git tag -a vX.Y.Z <commit> -m '...'`, затем push нужного tag.

Почему moving release tags — плохая практика?
?
Пользователи ожидают, что версия/tag неизменяемо указывает на один release commit. Перемещение ломает воспроизводимость и доверие к артефактам.

Как узнать, содержит ли релизная ветка конкретный fix commit по ancestry?
?
`git merge-base --is-ancestor <fix> <release-tip>`; но после squash/cherry-pick логически тот же fix может не иметь исходный commit как предка.

Как проверить наличие логически эквивалентного cherry-picked patch между ветками?
?
Можно использовать `git cherry`/patch-id-подобное сравнение, а не только ancestry по hashes.

Что показывает `git cherry -v upstream head`?
?
Сравнивает patches commits в `head` с upstream и помечает, есть ли patch-equivalent изменения в upstream, что полезно после cherry-pick/rebase.

Почему один и тот же patch может иметь разные commit IDs?
?
Commit ID включает tree, родителей и metadata, тогда как patch-equivalence оценивает изменение содержимого независимо от конкретной commit identity.

Что значит 'рабочая директория чистая', если `git status` clean?
?
Нет tracked изменений относительно index/HEAD и обычно нет показываемых untracked-файлов; это не означает, что нет ignored-файлов или внешнего состояния.

Может ли `git status` быть clean, а локальная ветка отличаться от remote?
?
Да. Clean относится к working tree/index, а ветка может быть ahead/behind/diverged относительно upstream.

Почему Git-команды часто разделяют данные и refs?
?
Объекты immutable и могут переиспользоваться, а refs — дешёвые подвижные указатели. Поэтому создание/удаление веток почти мгновенно.

Как объяснить, почему branch в Git 'лёгкая'?
?
Это в основном маленькая ref на commit, а не копия всех файлов или отдельная полная история.
