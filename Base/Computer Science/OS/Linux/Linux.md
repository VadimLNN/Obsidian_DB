> Основано на блоке **Linux** из приложенной DevOps RoadMap.  
> Цель конспекта — не просто перечислить команды, а собрать в одном месте теорию, команды, практику и типовые вопросы с собеседований из roadmap.

---

# 1. Почему Linux важен для DevOps

Linux — один из самых важных и больших блоков в DevOps.

С ним DevOps работает постоянно:

- серверы;
- виртуальные машины;
- контейнеры;
- Kubernetes;
- сервисы;
- логи;
- сеть;
- процессы;
- файловые системы;
- мониторинг ресурсов.

Основная задача на этом этапе — научиться не просто пользоваться Linux, а **понимать, что происходит с системой и почему она работает или не работает**.

# 4. Потоки и перенаправления

В Linux у процессов есть три стандартных потока:

```text
stdin   — стандартный ввод
stdout  — стандартный вывод
stderr  — стандартный поток ошибок
```

---

## 4.1. Перенаправление stdout

```bash
command > file.txt
```

Перезаписывает файл.

```bash

```

Добавляет данные в конец файла.

---

## 4.2. Перенаправление stderr

```bash
command 2> errors.log
```

---

## 4.3. stdout + stderr

```bash
command > output.log 2>&1
```

Оба потока записываются в один файл.

# 5. Pipes

Pipe:

```bash
|
```

Передаёт stdout одной команды в stdin другой.

Пример:

```bash
ps aux | grep nginx
```

Логика:

```text
ps aux
   ↓
вывод процессов
   ↓
grep nginx
   ↓
остаются строки с nginx
```

Pipes — одна из ключевых вещей при работе DevOps с Linux.

# 10. Состояния процессов

В roadmap выделены основные состояния.

| Состояние | Код | Что означает |
|---|---|---|
| Running | `R` | процесс выполняется |
| Sleeping | `S` | процесс спит и ждёт |
| Uninterruptible | `D` | процесс ждёт I/O |
| Zombie | `Z` | процесс завершён, но запись о нём осталась |
| Stopped | `T` | процесс остановлен |

---

## Zombie-процесс

Zombie:

```text
процесс уже завершился,
но запись о нём всё ещё существует в таблице процессов
```

Это частый вопрос на собеседованиях.

| Сигнал | Номер | Назначение |
|---|---:|---|
| `SIGTERM` | 15 | нормальное завершение |
| `SIGKILL` | 9 | принудительное завершение |
| `SIGHUP` | 1 | hangup / часто используется для перечитывания конфигурации |

| `SIGUSR1` | 10 | пользовательский сигнал |
| `SIGUSR2` | 12 | пользовательский сигнал |

# 15. `/proc`

`/proc` — псевдофайловая система.

В ней находится информация:

- о ядре;
- о процессах;
- о состоянии системы.

Например:

```bash

```



# 17. Пример systemd unit

Roadmap рекомендует взять простой HTTP-сервис и оформить его как systemd-службу.

Пример структуры:

```ini
[Unit]
Description=My HTTP Service
After=network.target

[Service]
ExecStart=/usr/bin/python /opt/app/server.py
Restart=always

[Install]
WantedBy=multi-user.target
```

Идея:

```text
Linux запускается
      ↓
systemd
      ↓
запускает сервис
      ↓
если сервис падает
      ↓
Restart=always
      ↓
сервис поднимается снова
```

# 42. Практика: свой systemd-сервис

Roadmap предлагает:

> взять любой простой HTTP-сервис и оформить его как systemd unit.

Требования:

- автозапуск;
- рестарт при падении;
- лимиты памяти через cgroups;
- после `kill -9` сервис должен подняться снова.

---

## Проверка

Например:

```bash
systemctl status myapp
```

Получить PID:

```bash
ps aux | grep myapp
```

Убить:

```bash
kill -9 <PID>
```

Проверить:

```bash
systemctl status myapp
```

Если unit настроен правильно — сервис должен снова работать.

# 49. Финальная практика перед Docker

Перед переходом к Docker попробуй выполнить всё на обычной Linux-машине или VM.

## Задача

Поднять:

```text
Frontend
Backend
Database
```

без Docker.

---

## Что должно получиться

```text
Linux
│
├── frontend
│
├── backend
│   └── systemd unit
│
├── database
│
└── logs
```

---

## Проверка

Ты должен уметь ответить:

```text
Какой процесс запущен?
Какой у него PID?
Какой порт он слушает?
Где его логи?
Сколько он использует RAM?
Что произойдёт после kill?
Как его перезапустить?
Как включить автозапуск?
Почему сервис не стартует?
Как проверить свободное место?
Как проверить inode?
Как проверить RAM?
Как посмотреть Load Average?
```

Если эти вопросы уже не вызывают ступор — Linux-база для следующего этапа DevOps сформирована.

# 50. Что дальше

Согласно roadmap, после Linux следующий крупный этап:

```text
Linux
   ↓
сети
   ↓
Docker
   ↓
CI/CD
   ↓
Ansible
   ↓
Kubernetes
```

Не нужно пытаться знать Linux полностью перед Docker.

Критерий перехода дальше:

> ты умеешь самостоятельно поднять приложение на Linux, запустить его как сервис и диагностировать базовые проблемы процессов, памяти, диска, логов и сети.
