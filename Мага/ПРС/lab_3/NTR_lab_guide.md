## 1. Что в итоге мы строим

Архитектура будет такой:

```
                         Интернет
                            │
               ┌────────────┴────────────┐
               │                         │
            Узел 1                    Узел 2
         NTP основной              NTP резервный
      192.168.56.103            192.168.56.104
               │                         │
               └──────────┬──────────────┘
                          │
                  Локальная сеть
                   192.168.56.0/24
                          │
               ┌──────────┴──────────┐
               │                     │
            Узел 3                Узел 4
        MariaDB Master A       MariaDB Master B
       192.168.56.105         192.168.56.106
               │                     │
               └─────────┬───────────┘
                         │
                 Служебная сеть
                   10.10.10.0/24

               node3: 10.10.10.3
               node4: 10.10.10.4
```

Смысл разделения сетей следующий.

**Внешняя сеть** нужна верхним узлам для обращения к внешним NTP-серверам.

**Локальная сеть `192.168.56.0/24`** связывает все четыре машины. По ней распространяется точное время.

**Служебная сеть `10.10.10.0/24`** существует только между узлами 3 и 4. По ней будет идти трафик репликации MariaDB.

Это хорошо соответствует схеме из задания: узлы 1–2 находятся ближе к внешней сети, все узлы связаны общей локальной сетью, а узлы 3–4 дополнительно имеют отдельную внутреннюю сеть.

У тебя первые две машины уже можно оставить с адресами `192.168.56.103` и `192.168.56.104`; тогда новые адреса логично продолжить `.105` и `.106`.

# 2. Настройка сетей VirtualBox

Здесь важно сначала правильно спроектировать сеть, потому что и NTP, и репликация MariaDB зависят от того, через какой интерфейс проходит трафик.

Я бы сделал так:

|Узел|Внешняя сеть|Локальная сеть|Служебная сеть|
|---|---|---|---|
|node1|NAT / NAT Network|`192.168.56.103`|—|
|node2|NAT / NAT Network|`192.168.56.104`|—|
|node3|—|`192.168.56.105`|`10.10.10.3`|
|node4|—|`192.168.56.106`|`10.10.10.4`|

Для локальной сети можно продолжить использовать твой существующий `vboxnet0`:

```
192.168.56.0/24
```

Для node3 и node4 создаём VirtualBox **Internal Network**, например:

```
dbnet
```

Название должно быть одинаковым на обеих машинах.

То есть для `node3`:

```
Adapter 1: Host-only Adapter → vboxnet0
Adapter 2: Internal Network → dbnet
```

Для `node4`:

```
Adapter 1: Host-only Adapter → vboxnet0
Adapter 2: Internal Network → dbnet
```

А node1 и node2 получают:

```
Adapter 1: NAT / NAT Network
Adapter 2: Host-only Adapter → vboxnet0
```

### Зачем отдельная сеть для БД

Технически MariaDB можно было бы реплицировать по `192.168.56.0/24`.

Но тогда отдельная служебная сеть из задания вообще не использовалась бы.

Кроме того, разделение сетей — нормальная серверная практика:

```
пользовательский/управляющий трафик
              │
              └── 192.168.56.0/24

репликация базы данных
              │
              └── 10.10.10.0/24
```

Таким образом, MariaDB можно вообще не публиковать в основной локальной сети.

# 3. Проверяем сетевую конфигурацию

На каждой машине:

```
ip -br a
```

Команда показывает сетевые интерфейсы в компактном виде.

Например, на node3 должно быть примерно:

```
lo       UNKNOWN 127.0.0.1/8
enp0s3   UP      192.168.56.105/24
enp0s8   UP      10.10.10.3/24
```

На node4:

```
enp0s3   UP      192.168.56.106/24
enp0s8   UP      10.10.10.4/24
```

Названия `enp0s3` и `enp0s8` могут отличаться. Поэтому ориентироваться надо **не на имя интерфейса, а на IP-адрес**.

Проверяем общую сеть:

```
ping 192.168.56.103
ping 192.168.56.104
ping 192.168.56.105
ping 192.168.56.106
```

А между node3 и node4 дополнительно:

```
ping 10.10.10.4
```

и с node4:

```
ping 10.10.10.3
```

Это важная проверка. Если сеть не работает, бессмысленно начинать настройку NTP или MariaDB — проблема будет выглядеть как проблема приложения, хотя на самом деле пакеты просто не доходят до другой машины.

# 5. Как должна работать синхронизация времени

Прежде чем писать конфиги, нужно понять иерархию.

Получается такая цепочка:

```
0.pool.ntp.org ─┐
                ├── node1 ─── node2
1.pool.ntp.org ─┘      │       │
                       └───┬───┘
                           │
                     node3 / node4
```

У NTP есть понятие **stratum**.

Упрощённо:

```
эталонные часы       stratum 0
       ↓
NTP-сервер           stratum 1
       ↓
другой NTP-сервер    stratum 2
       ↓
клиент               stratum 3
```

Конкретные цифры в нашей лабораторной могут отличаться, потому что публичный NTP-сервер сам может быть, например, `stratum 2`.

Главное, чтобы была видна иерархия:

```
Internet NTP
     ↓
node1
     ↓
node2
```

а node3 и node4 использовали node1/node2.

# 6. Почему используем Chrony

Для NTP можно использовать несколько реализаций.

Для Linux удобно использовать:

```
chrony
```

`chronyd` реализует протокол NTP и умеет одновременно:

- быть NTP-клиентом;
- синхронизировать локальные часы;
- быть NTP-сервером для других машин;
- показывать состояние источников времени;
- ограничивать доступ по сети.

То есть один и тот же демон подходит для всех четырёх машин.

На всех четырёх машинах:

# 8. Настройка node1

Node1 выполняет две роли:

```
NTP client → получает время из интернета
NTP server → отдаёт время локальной сети
```

Открываем:

```
sudo nano /etc/chrony/chrony.conf
```

В конфигурации могут уже быть строки вроде:

```
pool ...
server ...
```

Их лучше закомментировать, чтобы точно понимать, какие источники используются.

Добавляем:

```
server 0.pool.ntp.org iburst
server 1.pool.ntp.org iburst

allow 192.168.56.0/24

local stratum 8
```

Разберём каждую часть.

### Два `server`

```
server 0.pool.ntp.org iburst
server 1.pool.ntp.org iburst
```

Именно два сервера указаны не случайно: в задании требуется **не менее двух внешних NTP-серверов**. lab03

`iburst` говорит chrony при старте быстрее выполнить первоначальную серию запросов, чтобы не ждать обычного длительного интервала NTP.

---

### `allow`

```
allow 192.168.56.0/24
```

Chrony теперь разрешает машинам из:

```
192.168.56.0 — 192.168.56.255
```

использовать node1 как NTP-сервер.

Это непосредственно реализует требование, что источник времени должен быть доступен только локальной сети. lab03

Мы **не пишем**:

```
allow all
```

потому что тогда NTP-сервер сможет обслуживать клиентов из других сетей.

---

### `local stratum`

```
local stratum 8
```

Эта настройка позволяет серверу продолжать выступать источником времени на основе собственных локальных часов, даже если внешний NTP временно недоступен.

Stratum здесь специально достаточно большой, чтобы такой источник считался хуже настоящих внешних NTP-серверов.

---

После изменения:

```
sudo systemctl restart chrony
sudo systemctl enable chrony
```

Проверяем:

```
chronyc sources -v
```

В таблице должно появиться что-то вроде:

```
^* ntp-server-1
^+ ntp-server-2
```

Знаки важны:

```
* — текущий выбранный источник времени
+ — источник подходит и используется при расчётах
- — источник признан менее подходящим
? — источник пока недоступен
```

Ещё полезная команда:

```
chronyc tracking
```

Она показывает:

```
Reference ID
Stratum
System time
Last offset
Leap status
```

```

```

```

# 12. Переходим к MariaDB

Вторая часть задания требует:

```
node3 ↔ node4
```

Причём оба сервера должны быть активными.

Обычная репликация часто выглядит так:

```
Master → Slave
```

Писать можно только в Master.

Здесь нужна:

```
Master ↔ Master
```

То есть:

```
запись в node3
       ↓
появляется в node4

запись в node4
       ↓
появляется в node3
```

# 13. Почему MariaDB связываем через 10.10.10.0/24

Для репликации будем использовать:

```
node3 10.10.10.3
node4 10.10.10.4
```

а не `192.168.56.x`.

Это делает назначение служебной сети явным:

```
192.168.56.0/24
        │
        └── управление + NTP

10.10.10.0/24
        │
        └── MariaDB replication
```

# 15. Как вообще работает репликация MariaDB

MariaDB записывает изменения базы в специальный журнал:

```
binary log
```

Например, node3 выполняет:

```
INSERT INTO book_orders ...
```

Далее происходит:

```
MariaDB node3
      │
      ├── изменяет свою таблицу
      │
      └── записывает событие в binary log
                     │
                     ▼
                MariaDB node4
                     │
                     └── повторяет изменение
```

В обратную сторону работает аналогичный механизм.

Поэтому каждый сервер одновременно является:

```
master — отдаёт свой binlog

slave — получает binlog второго сервера
```

Отсюда и название:

```
master-master
```

# 16. Конфигурация node3

Открываем:

```
sudo nano /etc/mysql/mariadb.conf.d/50-server.cnf
```

В секции:

```
[mysqld]
```

задаём:

```
bind-address = 10.10.10.3

server-id = 3

log_bin = /var/log/mysql/mariadb-bin
binlog_format = ROW
log_slave_updates = ON

auto_increment_increment = 2
auto_increment_offset = 1
```

## Что означает каждая настройка

### `bind-address`

```
bind-address = 10.10.10.3
```

MariaDB принимает сетевые подключения именно через служебную сеть.

В результате порт `3306` не выставлен без необходимости во все доступные сети.

---

### `server-id`

```
server-id = 3
```

Каждый участник репликации обязан иметь уникальный идентификатор.

Для node4 будет:

```
server-id = 4
```

MariaDB благодаря этому понимает, какой сервер создал конкретное событие.

---

### `log_bin`

```
log_bin = /var/log/mysql/mariadb-bin
```

Включает binary log.

Без него сервер не сможет нормально быть источником репликации.

---

### `binlog_format = ROW`

```
binlog_format = ROW
```

MariaDB будет передавать фактические изменения строк.

Это обычно надёжнее для репликации, чем попытка повторно исполнять исходный SQL на второй машине.

---

### `log_slave_updates`

```
log_slave_updates = ON
```

События, полученные через репликацию, также помещаются в локальный binary log.

Для циклической/распределённой схемы это делает поведение топологии более последовательным.

---

# 17. Как избежать конфликтов ID

Это один из наиболее важных моментов задания.

Представим обычный `AUTO_INCREMENT`.

Node3 одновременно создаёт:

```
id = 1
```

и node4 создаёт:

```
id = 1
```

После репликации получаем:

```
Duplicate entry '1' for key PRIMARY
```

Чтобы этого не произошло, делим последовательность ID между серверами.

Node3:

```
auto_increment_increment = 2
auto_increment_offset = 1
```

Получит:

```
1
3
5
7
9
...
```

Node4:

```
auto_increment_increment = 2
auto_increment_offset = 2
```

Получит:

```
2
4
6
8
10
...
```

Поэтому два сервера могут независимо создавать новые строки.

# 19. Создаём пользователя репликации

Node3 должен разрешить node4 читать свой binary log.

На node3:

```
sudo mariadb
```

В MariaDB:

```
CREATE USER 'repl'@'10.10.10.4'
IDENTIFIED BY 'ReplicationPass123!';

GRANT REPLICATION SLAVE ON *.*
TO 'repl'@'10.10.10.4';

FLUSH PRIVILEGES;
```

На node4 создаём зеркальный вариант:

```
CREATE USER 'repl'@'10.10.10.3'
IDENTIFIED BY 'ReplicationPass123!';

GRANT REPLICATION SLAVE ON *.*
TO 'repl'@'10.10.10.3';

FLUSH PRIVILEGES;
```

Почему мы не создаём:

```
'repl'@'%'
```

?

Потому что `%` разрешает подключаться из любой сети.

Нам известны конкретные адреса серверов:

```
10.10.10.3
10.10.10.4
```

Поэтому безопаснее явно ограничить их.

# 20. Находим точки начала репликации

На node3:

```
SHOW MASTER STATUS;
```

Получим примерно:

```
+--------------------+----------+
| File               | Position |
+--------------------+----------+
| mariadb-bin.000001 |      732 |
+--------------------+----------+
```

Записываем:

```
NODE3_FILE = mariadb-bin.000001
NODE3_POS  = 732
```

Теперь node4:

```
SHOW MASTER STATUS;
```

Например:

```
NODE4_FILE = mariadb-bin.000001
NODE4_POS  = 755
```

### Что это означает

`File` — текущий binary log.

`Position` — место внутри этого журнала.

Когда мы говорим node3:

> начни получать события node4 начиная с позиции 755

он не будет воспроизводить старые операции.

После сохранения этих позиций до завершения настройки лучше ничего в БД не менять.

# 21. node3 начинает получать изменения от node4

На node3:

```
STOP SLAVE;

CHANGE MASTER TO
    MASTER_HOST='10.10.10.4',
    MASTER_USER='repl',
    MASTER_PASSWORD='ReplicationPass123!',
    MASTER_PORT=3306,
    MASTER_LOG_FILE='mariadb-bin.000001',
    MASTER_LOG_POS=755,
    MASTER_CONNECT_RETRY=5;

START SLAVE;
```

Здесь необходимо подставить **реальные значения node4**.

Логика:

```
node3
  │
  └── slave connection
           │
           ▼
        node4
```

На node4:

STOP SLAVE;

CHANGE MASTER TO

    MASTER_LOG_FILE='mariadb-bin.000001',
    MASTER_LOG_POS=732,
    MASTER_CONNECT_RETRY=5;

START SLAVE;
```

Опять же используем реальные значения:

```
NODE3_FILE
NODE3_POS
```

Теперь:

```
node3 ───────────► node4
  ▲                  │
  │                  │
  └──────────────────┘
```

Получается двусторонняя репликация.

# 23. Проверяем состояние

На обоих серверах:

```
SHOW SLAVE STATUS\G
```

Нас интересуют:

```
Slave_IO_Running: Yes
Slave_SQL_Running: Yes
```

В идеальном случае:

```
Seconds_Behind_Master: 0
```

Самые важные поля для диагностики:

```
Last_IO_Error:
Last_SQL_Error:
```

Если они пустые — это хорошо.

### Разница IO и SQL потока

`Slave_IO_Running` отвечает примерно за:

```
может ли сервер подключиться ко второму серверу
и получать его binary log
```

`Slave_SQL_Running`:

```
может ли MariaDB применять полученные изменения
к своей базе
```

Поэтому:

```
IO = No
```

чаще говорит о сети, адресе, пользователе или пароле.

А:

```
SQL = No
```

чаще означает конфликт данных или ошибку SQL.

# 29. Очень важный момент про «отсутствие конфликтов»

Нужно правильно понимать формулировку задания.

Обычная master-master репликация **не является полноценным механизмом автоматического разрешения любых конфликтов**.

Наш механизм предотвращает наиболее очевидный конфликт:

```
node3 создаёт id=1
node4 создаёт id=1
```

Но если одновременно выполнить:

на node3:

```
UPDATE book_orders
SET status='issued'
WHERE id=1;
```

а на node4:

```
UPDATE book_orders
SET status='cancelled'
WHERE id=1;
```

возникает уже логический конфликт.

MariaDB не знает, какое решение «правильное».

Поэтому для лабораторной формулировка такая:

> Конфликты автоматически генерируемых первичных ключей предотвращены разделением пространства AUTO_INCREMENT между двумя серверами. Одновременное изменение одной и той же логической записи на разных master-узлах необходимо исключать организационно.

Это технически корректнее, чем говорить, что master-master полностью избавляет от конфликтов.

В реальных системах для более сложной multi-primary работы используют другие архитектуры, например Galera Cluster или single-writer схему.

# 31. Полная логика лабораторной

В итоге система выглядит так:

```
                 NTP SERVER A
                      │
Internet ─────────► NODE 1
                      │
                      ▼
                   NODE 2
                 NTP SERVER B
                  │       │
             ┌────┘       └────┐
             ▼                 ▼
           NODE 3            NODE 4
           NTP client        NTP client
              │                 │
              │                 │
              ├──── MariaDB ────┤
              │   master ↔      │
              │        master   │
              │                 │
           10.10.10.3       10.10.10.4
```

Здесь уже используются сразу несколько принципов распределённых систем:

**Иерархия сервисов**

```
внешние NTP
↓
локальные NTP
↓
клиенты
```

**Отказоустойчивость**

```
node3/node4 имеют два источника времени
```

**Репликация**

```
MariaDB node3 ↔ MariaDB node4
```

**Разделение сетей**

```
управляющая сеть
+
служебная сеть
```

**Предотвращение конфликтов идентификаторов**

```
node3: 1,3,5,7...
node4: 2,4,6,8...
```
